## 1. Security invariants

1. No plaintext password, master key, identity private key, message content, or attachment key is written to disk or logs. Released file bytes stay in zeroizing memory until the user stores them encrypted or the native OS save dialog writes them to a user-chosen path; no other plaintext file is created.
2. All peer input is untrusted until verified: transport (Noise/PeerId), envelope (signature/version/replay), conversation (MLS), file (hash/format/scan/policy).
3. No core function requires a centralized service. Optional relay/DHT peers are user-operated and see ciphertext/metadata only. Every optional capability is off/empty by default; observations are advisory and never promote trust, contact verification, or delivery.
4. Delivery, verification, connection, and scanning statuses reflect observed facts; unknown states are shown as unknown.
5. Cryptographic failures fail closed: close stream, drop message, quarantine file, emit security event.

## 3. Network security implemented in Milestone 4

- Direct connect uses libp2p TCP + Noise + Yamux with the independently generated `Transport` role key from the encrypted vault bundle imported through the stable protobuf Keypair encoding. The network PeerId matches that certified transport key; wire envelopes and setup frames use separate certified `Application` role keys.
- Dial addresses must end in `/p2p/<peer-id>`; user-supplied bootstrap/relay addresses follow the same rule and must not contain `/p2p-circuit`. Noise authenticates that PeerId before a connection is reported; a wrong PeerId fails the handshake.
- No bootstrap peers, DHT, mDNS, identify, ping, relay, AutoNAT, DCUtR, UPnP, or developer-operated endpoints are configured by default. The default listen address is `/ip4/0.0.0.0/tcp/0`. M13 adds opt-in user-configured discovery/relay/NAT/identify behaviours; none is enabled or contacted in the default path.
- Connection status comes only from Swarm events. The GUI does not turn a button press into a "connected" indicator.
- `identify` is off by default. If explicitly enabled it hides listen addresses and bounds protocol/agent strings, but advertised protocol lists are still not cross-checked. A connected PeerId, discovery candidate, or identify result is not a fingerprint-verified contact.
- `/p2p-messenger/message/1`, `/p2p-messenger/mls-setup/1`, `/p2p-messenger/file/1`, and M13's `/p2p-messenger/control/1` are negotiated separately over the authenticated connection, each with a bounded 1 MiB request/response frame. Message `SentToPeer` never claims delivery; setup `SentToPeer` never claims group join; file `SentToPeer` never claims transfer completion; `ControlEvent::SentToPeer` never claims an application capability or receipt. Only verified application receipts and setup acknowledgements advance their states; only a verified file manifest acknowledgement advances file integrity status. M12/M13 hand-written `Debug` implementations for all four event types report identifier, peer, and byte length but never print opaque request or response bytes.
- MLS payload encryption, signed setup, and signed group-control frames are implemented for two- and three-member groups; a live connection still does not prove that the peer is the intended contact. M13's control protocol is opaque transport plumbing and carries no capability, presence, receipt, delivery, trust, or safety semantics.
- Direct peers see IP addresses, connection timing, and traffic sizes. Q1 relay-only routing avoids the destination peer's direct view under explicit configuration, and Q5 routes dials through a configured SOCKS5 proxy without a local listener; neither establishes metadata privacy, Tor identity, or anonymity.

### Milestone 6 network resilience

- A redial attempt is created only for an address the user explicitly supplied. Retry count and delay growth are capped, and a user disconnect suppresses redial until a fresh explicit dial. `RedialState` is scheduler intent, never a connection, delivery, or contact-verification claim.
- Duplicate pending dials are rejected until the first dial settles. Established connections are capped globally, per authenticated PeerId, and per observed IP; excess connections are closed.
- An aggregate sliding per-peer window caps inbound application request count and request bytes for all four bounded protocols before the application decodes them. Derived per-protocol reservations keep one saturated protocol from consuming another protocol's share, and a rejected request is charged to neither window. Rejected requests produce honest transport failure events.
- These controls limit resource use; they do not authenticate the human behind a PeerId, prevent Sybil identities, hide metadata, or replace application-level authorization.

### Milestone 13 optional network privacy

- Every optional behaviour is configured off/empty by default and applied only when the network worker starts; changing settings requires lock/unlock. No developer-operated peer is compiled in.
- mDNS and Kademlia produce advisory candidate counts only. Kademlia requires user-supplied direct bootstrap addresses. Discovered peers are never auto-dialed, saved as contacts, trusted, or marked fingerprint-verified.
- Relay client/server modes require explicit user configuration and are bounded. With pinned `libp2p 0.57.1`, the relay client transport is Noise-upgraded like direct TCP: relay operators can observe PeerIds, IP addresses, timing, and sizes and can deny service, but they forward opaque bytes and receive no application plaintext, private keys, message keys, or file keys. Explicit server mode enables the relay HOP status only for concrete advertised listen addresses. Relayed connections are separately capped and counted from observed `is_relayed()` connections; a relayed path is not a trust or delivery claim.
- `send_file` and inbound file requests refuse observed relayed paths as a conservative metadata/policy choice until a dedicated relay-safe file-key/transport design exists. The signed M7 file content key is inside Noise-protected bytes; the policy does not assume a relay can read it.
- AutoNAT and DCUtR are best-effort observations/hole-punch attempts, not universal NAT traversal. Ping is a low-frequency liveness observation, not application health or delivery. Identify hides listen addresses and bounds peer-provided strings, but still reveals a bounded protocol/agent description.
- `/p2p-messenger/control/1` uses the bounded opaque codec. The controller drains control, discovery, relay, NAT, and identify queues only to update the cached privacy snapshot; it never promotes an observation into a contact, verified peer, capability, receipt, or delivery state.
- `NetworkPrivacyStatus` separates local configured flags/counts from values updated by real libp2p events. `relay_reservations`, `relay_circuits`, and `identified_peers` count events observed since worker startup, not live state; `relayed_connections` is the latest live count from a transport event. AutoNAT v1 reports no confidence value, so none is emitted. The GUI labels cumulative observations as "observed since startup" and shows limitation rows rather than claiming anonymity, universal connectivity, or file transfer over relays.
- Two-machine LAN, NAT, volunteer-relay, and real proxy/Tor verification remains an external test. Q5 adds a configured SOCKS5 route but no verified Tor/I2P/mixnet support, metadata confidentiality, proxy identity, or unlinkability claim.

### Privacy follow-up Q1/Q2/Q5 (not a numbered milestone)

- Q1 relay-only policy requires relay-client mode, rejects direct application dials and direct listeners, validates circuit destinations against configured relays, and gates application traffic on an observed relayed path. The relay still sees IP, PeerId, timing, and sizes; file-over-relay remains disabled. A real local relay integration test proves circuit-only listeners, a reservation/circuit, and relayed alice-to-bob connectivity; no two-machine verification is claimed.
- Q2 pads MLS application plaintext, including receipts, to one of 15 fixed buckets from 64 to 786432 bytes before encryption. The tag-`1` record has a 5-byte original-length header; receive strips it only when the length is an exact bucket, the tag is valid, the claimed length is in range, and the tail is zero. Malformed padding fails closed. This is coarse length hiding, not metadata confidentiality, timing defense, randomization, or outer-frame normalization.
- Q5 SOCKS5 route mode uses a SOCKS5-only libp2p transport with no direct listener or direct fallback, rejects hostname proxy addresses and local-resolution target forms, and passes `/dns4`/`/dns6` destinations to the proxy as domains. Noise/Yamux run over the proxy stream. Configuration conflicts with mDNS/AutoNAT/DCUtR fail closed; a fake-proxy test proves `example.onion` reaches the proxy as a domain CONNECT target.
- GUI wording distinguishes configured routes from observed facts: SOCKS5 status is “Configured (proxy identity and reachability not verified)”, and the anonymity row explicitly says proxy identity and reachability are not established. No status row claims Tor, anonymity, or unlinkability.
- Q3 clear-envelope metadata reduction and Q4 ephemeral delegated application keys remain design-only pending explicit wire/identity boundary decisions. No silent wire-version or identity change is made.

## 4. Messaging security implemented in Milestone 5

- Envelopes are canonical v2 records with fixed `P2P1` magic, version, conversation/message IDs, real MLS epoch, sender PeerId, certificate proof, sequence, untrusted timestamp, kind, MLS ciphertext payload, and a 64-byte Ed25519 `Application`-role signature over every field except the signature. Version 1 is rejected rather than negotiated.
- The embedded public key is bound into the signature and checked against the declared PeerId. A PeerId is only a multihash and cannot verify a signature by itself. Decoding rejects wrong magic, unknown versions, bad kind codes, oversized fields, truncated fields, and trailing bytes.
- Incoming envelopes are verified before replay state is touched. Conversation mismatches, epoch mismatches, duplicate message IDs, and regressed sender sequences are rejected. The replay cache is bounded, with a strict per-sender sequence high-water mark.
- `MlsConversation` uses OpenMLS 0.10.0-rc.1 with `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`. KeyPackage acceptance binds the expected PeerId bytes to the MLS BasicCredential and the expected raw Ed25519 public key to the leaf signature key. Welcome joining uses the original `MlsKeyPackage` provider so the in-memory private material is retained.
- On receive, MLS checks the group ID, epoch, member set, credential, and leaf signature key before returning plaintext. A valid envelope signed by a different peer over another member's MLS ciphertext is rejected. Decrypted bytes are held in a `Zeroizing` buffer and are not written to logs or the vault.
- Receipts use explicit `Delivered`/`Read` bodies, encrypted as MLS application messages. A receipt for an unknown message is rejected, and `SentToPeer` remains explicitly unconfirmed; no local send action creates a delivery claim.
- Envelopes are stored only as XChaCha20-Poly1305 ciphertext in schema v2 of the vault, with HMAC blind indexes for conversation/message lookup. Raw database/WAL/SHM sentinel scans cover message bytes. The legacy envelope load path can reverify opaque envelopes but cannot rebuild MLS receipts. With a vault session, Phase 4 loads MLS groups through the encrypted provider and restores receipt expectations from an authenticated application record, not from envelope records.
- MLS state is never written to disk in plaintext. Without a vault session it is lost on restart; with one, Phase 4 and P1e restore joined group/ratchet state, ready derived channel groups, channel policy, bounded pending operations, receipt expectations, and queued ciphertext with fail-closed validation, while setup KeyPackages/Welcomes and decrypted messages remain memory-only. The control-frame digest log is not a backup and does not restore MLS state. A valid signature authenticates control of the sender key; it does not prove the sender is the intended contact, so fingerprints must be compared out of band.
- `/p2p-messenger/message/1` uses libp2p request-response over Noise. The transport carries an opaque, bounded frame; it does not verify signatures or change delivery state. The application decodes and verifies envelopes before replay changes, and decrypts/verifies receipts before changing delivery state.
- `/p2p-messenger/mls-setup/1` carries signed `MLS1` frames. The signature binds the PeerId, public key, conversation ID, message code, and body; the controller checks the frame against the Noise-authenticated peer before passing KeyPackage or Welcome bytes to OpenMLS. The inviter waits for a verified `WelcomeAck` before showing `Joined`. A bounded 512-entry memory cache stores authenticated frame digests. Schema v4 additionally records already authenticated frames in a durable chained log of encrypted PeerId/digest/repeatability records with HMAC blind indexes (at most 4096 entries; fail closed when full or malformed); `<vault>/control.anchor` holds the AEAD-protected high-water mark and is verified by `Vault::unlock` together with every record, chain link, and blind index. `KeyPackageRequest` and `GroupJoinRequest` repeats remain idempotent and cannot overwrite a different transaction's pending state; KeyPackage responses, Welcomes, `GroupWelcome`, `GroupCommit`, and all acks are non-repeatable. `MessengerController::start_with_control_log` takes a cloned vault `Session` and rejects a vault/controller identity mismatch. This gives partial continuity across restart, not a replay-proof log or an external anchor.
- `MessengerController` keeps pending KeyPackages, decrypted text, and setup status in memory only; with a vault session it restores joined MLS groups and bounded pending/receipt/queue state from encrypted records. GUI delivery labels come from `DeliveryState::description()`; `ChatMessage::Debug`, `QueuedMessage::Debug`, and `SetupEnvelope::Debug` redact plaintext, ciphertext bodies, and setup bodies.
- The offline queue stores the signed MLS ciphertext envelope only, never the composed plaintext. With a vault session it is encrypted and restored after restart; without one it is memory-only and lost on lock. It is retried only after an observed `ConnectionState::Connected` event for that peer. Polling while disconnected cannot promote `Queued` to `SentToPeer`, and retry or restore cannot promote to `Delivered` without a verified MLS receipt. A raw database/WAL/SHM scan asserts that no queued plaintext reaches the vault.
- Wire and controller acceptance tests send an MLS-encrypted signed envelope and an MLS-encrypted receipt between two isolated instances, and complete the signed setup exchange before that traffic. Re-signing tampered ciphertext is rejected by MLS, and a foreign sender envelope carrying another member's ciphertext is rejected by the MLS sender binding. Tampered setup frames and wrong-peer signatures are rejected before MLS state changes. The GUI path uses the same controller and does not create independent delivery claims.

### Milestone 9 group security

- Codes `5`–`10` extend the same signed `MLS1` codec with group join, KeyPackage, Welcome, commit, and acknowledgement frames. Strict parsers reject unknown operations, bad target encodings, empty commits, malformed acknowledgements, trailing bytes, oversized frames, and tampered signatures before MLS state changes.
- The creator is the initial admin. Only that PeerId may start Add, Remove, or self-Update. `check_admin` also requires a joined conversation and no pending operation. `add_member` requires a direct connection; `remove_member` denies self-removal and nonmembers.
- The admin merges a commit locally, broadcasts it to required existing members, and clears `pending_operation` only after the group Welcome and all required CommitAck frames are verified. Messages and further group changes are blocked while pending; disconnected required members can leave it pending until reconnect. No timeout, rollback, or partial completion is claimed.
- A new member joins at the Add commit's new epoch through its signed Welcome and is excluded from that commit's acknowledgement set, so it never applies the commit that created its epoch. The admin identity is learned from the signed Welcome sender after the join request exchange.
- MLS `process_commit` verifies the commit sender's signature/key and the declared operation/target before merging. Remove advances remaining members' epoch; the removed member stays on the excluded epoch and cannot decrypt future group traffic. Stale-epoch ciphertext from the removed member is rejected.
- Text is one signed MLS envelope broadcast to all current members with one ciphertext queue copy per disconnected recipient. Local `Delivered` requires verified receipts from every expected member; transport sends and partial receipts do not create a delivery claim.
- Admin authority is local client policy from signed frames, not a complete cryptographic role system. P6 adds local device-signed role-delegation primitives, but no directory, GUI trust anchor, or admin role change is wired; external commits remain unimplemented. With a vault session, encrypted MLS state restoration of explicitly `Joined` groups, ready derived channel groups, bounded pending operations, receipts, and ciphertext queue is implemented with fail-closed validation; setup material and decrypted text are not restored. Setup/group-control frames have a bounded exact-frame digest cache plus request correlation and state guards, backed by a schema v4 chained digest log and vault anchor for partial local continuity; this is not replay-proof, does not detect a full vault restored with its anchor, and the digest log itself does not restore MLS state.

### Milestone 10 channel security

- Channels reuse the signed v2 envelope and MLS plaintext path. Parent policy stays in a bounded `CHN1` body carrying `channel_id`, revision, and create/rename/set-members data inside parent MLS application plaintext; P1d encrypts non-default text and receipts in a signed, bound derived MLS group. M10 introduced no new wire protocol or setup code; P2 later changed the canonical envelope to v2 in place.
- The outer envelope signature and MLS sender binding authenticate the writer. Strict decoding rejects wrong magic, unknown kinds, invalid PeerIds, empty/duplicate/oversized member sets, invalid names/text, truncation, trailing bytes, and oversized frames.
- The creator/admin alone may create, rename, or change channel membership. Create requires revision `1`; rename and member changes require the current revision plus one. Members must already belong to the MLS group. The default `[0; 16]`/`general` channel is present in every joined conversation and tracks current membership.
- Text is accepted from an authenticated MLS member who is also in that channel's local allowed set, and restricted sends go only to allowed recipients. Invalid or unauthorized frames receive no delivery receipt and only a static `last_error` category.
- Channel metadata changes do not create MLS commits. Their `acknowledged` state is derived from receipts for the last locally composed policy frame; custom channels are not replayed to later joiners.
- **Channels are not cryptographic access control.** Every MLS group member holds the group keys, so a member could decrypt a channel ciphertext it obtains. Restricted delivery reduces ordinary exposure but cannot provide a separate confidentiality boundary. Per-channel MLS keys are not implemented.
- Channel names/text are redacted from `Debug`; with a vault session, joined-group channel policy and ready derived channel groups restore from authenticated encrypted application records, while decrypted channel text remains memory-only and no plaintext channel body is written to disk by the controller.

## 5. File security workflow

Implemented in M7 and extended in M8:

- Sender: validate base name and bounded size → compute per-chunk and full SHA-256 → derive a signed manifest commitment → generate a fresh 32-byte content key → send it only inside the signed offer over the Noise-authenticated connection → encrypt each chunk with XChaCha20-Poly1305 and bound AAD → advance only on explicit signed acknowledgements. Active transfers have an inactivity deadline and a local abort, while release decisions can be cancelled only after integrity verification; an already queued worker request cannot be withdrawn through the pinned request-response API.
- Receiver: verify the signed offer against the authenticated PeerId → create a `0700` quarantine directory → verify each signed chunk's AEAD tag in memory before writing ciphertext → verify the signed manifest against the commitment, every chunk hash, and the full SHA-256 → write only a hash manifest record to quarantine. Plaintext and the content key are never written to disk.
- The joined MLS conversation is required before a transfer starts, and only one transfer per peer is active. Integrity status comes from verified signed frames; transport sends and acknowledgements alone never mark a transfer complete.
- `IntegrityVerified` means byte-for-byte agreement with the signed hashes only. After verification and before scanning, `ScanStatus` is `Unavailable`; before verification it is `NotApplicable`. There is no `Clean`, `Safe`, or `Scanned` status produced by integrity checking.
- `p2p-security` defines an application-supplied `FileScanner` taking bounded in-memory bytes (`name` plus plaintext bytes) and returning one exact category: `CleanNoThreatDetected`, `ThreatDetected`, `Unavailable`, `Failed`, or `UnsupportedFormat`. `NoScanner`/default configuration returns `Unavailable` without inspecting bytes. The scanner never receives a disk path, and this interface writes no plaintext.
- Only `SecurityConfig::scan` can create a `ScanOutcome`; the private outcome and format fields prevent an application caller from fabricating a clean result or validated format. `SecurityConfig::scan` first checks the claimed extension against the bytes; a mismatch short-circuits to `UnsupportedFormat` before an independent scanner is invoked. `p2p-chat::scan_file` reassembles plaintext only in a zeroizing buffer, invokes the configured scanner, and stores the exact category and validated format on the transfer. With no scanner configured, a supported format records `Unavailable`; a mismatch records `UnsupportedFormat`.
- Structural validation is dependency-free and deliberately narrow: UTF-8 text without disallowed control bytes, PNG signature/chunk/CRC/IHDR/IEND structure, and GIF header/block/trailer structure. It is not malware detection, a general media parser, or a MIME sniffer.
- `ReleaseApproval` moves a transfer from `NotReady` to `Pending` only after a clean scan, validated format, cross-platform safe base name, non-empty bounded size/chunk count under an unraisable 64 MiB cap, and explicit extension allowlist. `approve_file` records the user's explicit decision; `release_file` still requires `Approved` and returns plaintext only in a zeroizing `ReleasedFile` buffer. `cancel_file` applies only to an integrity-verified transfer, is terminal for release, and retains verified ciphertext. Active transfers have an inactivity deadline and a separate `abort_file` that stops application progress, drops pending response bookkeeping, zeroizes the key, and deletes incomplete quarantine ciphertext; an in-flight worker request cannot be withdrawn through the pinned request-response API, so late responses are ignored. Default policy allows no extensions, so every release is denied by default. Release does not write plaintext to disk and does not call anything safe or clean.
- Extension checking alone is never treated as format validation. A clean antivirus result is defence in depth, never a guarantee.

M8 release/storage boundary: `ReleasedFile` is copied by the desktop application into an encrypted attachment store with a random per-file key, blind index, encrypted metadata, and a digest recheck on read. The native-only OS save dialog is the only plaintext disk write and requires a user-chosen path; a cancelled dialog writes nothing. M12 sanitizes the suggested name, refuses a pre-existing symlink, creates the file as `0600` on Unix, syncs before returning, and reports only static errors. Stored-attachment deletion is explicit; M12 checks blob paths for symlinks before removing the database record. Quarantine deletion defaults to `Retain`; under `Explicit` it requires a verified transfer that was released or cancelled. Neither deletion action implies the other, grants a clean status, cancels the network transfer, or guarantees secure erasure on SSD/CoW storage.

Still not implemented: general format/MIME parsing, transport-level cancellation of an already queued worker request, backup/restore, and a configured real scanner. Until a real scanner returns `CleanNoThreatDetected` for a structurally validated file, the UI must say **"Scanning unavailable"** and no release path may succeed.

## 6. Local storage and privacy

- Sensitive fields are AEAD ciphertext before they reach SQLite. Blind indexes (HMAC with a dedicated subkey) are used where lookups are required. Implemented for the profile vault and settings in M3 and message envelopes in M5, including raw database/WAL/SHM sentinel scans.
- Schema v4 adds transactional `control_log` (`sequence`, `record_bi`, `ciphertext`, `chain_hash`) and `control_state` tables for authenticated control-frame digests. The AEAD-protected `<vault>/control.anchor` high-water mark (atomically replaced via `control.anchor.tmp`) lets unlock detect a database-only rollback or a tampered/missing anchor after a nonempty log; a full vault restored with its anchor is not locally detectable without an external anchor.
- Search indexes are a design target: any future index must use encrypted/keyed lookups, and plaintext full-text indexes will not be used. No search index exists yet.
- M7 quarantines incoming ciphertext in `0700` directories with `0600` chunk files on Unix (Windows ACL hardening remains a target). M8 attaches released bytes only as encrypted blobs with encrypted metadata; the native-only OS save dialog writes plaintext solely to a user-chosen path and writes nothing if cancelled. M12 refuses symlinked final paths when opening a vault or creating a quarantine directory on Unix, checks attachment blob paths for symlinks before record deletion, and hardens the save helper described above. Stored attachments and quarantine ciphertext are deleted only by separate explicit actions; filesystem deletion is not secure erasure on SSD/CoW storage.
- Encrypted backups with a separate recovery passphrase and an encrypted identity export are a design target. No backup/restore code or UI exists yet.

## 7. Logging policy

Log: protocol versions, PeerIds (public), connection state transitions, error categories, transfer IDs, security event categories. Never log: passwords, derived keys, private keys, message plaintext, attachment bytes, full file paths where not needed, QR payloads containing private material (they never do). Setup and group-control `Debug` output reports body lengths and redacts KeyPackage, Welcome, and commit bytes. Channel frame and `ChannelInfo` `Debug` output redacts channel names and text. M12 transport event `Debug` output redacts message, setup, and file request/response bytes; M13 extends that to control frames and bounds identify-provided strings; static failure reasons and public identifiers remain. M12 also rejects oversized contact URIs and identity envelopes before decode/KDF work so hostile inputs cannot turn into verbose structured errors. `Vault` and `FileConfig` diagnostics redact local directory paths, and unknown contact-URI query keys produce a static error instead of reflecting attacker text. Debug builds must not print secret buffers; use `zeroize` and avoid `Debug` derives on secret wrappers. The repository-wide print/log/`Debug` inventory found no password, private-key, plaintext, or opaque-frame output, and `scripts/check_diagnostics.py` enforces those rules with fail-closed self-tests; in the final post-Q local gate it checked 64 Rust sources. Historical CI results are not evidence for this uncommitted workstream.

## 8. What we explicitly do not claim

- We do not claim antivirus scanning proves a file is safe.
- We do not claim metadata privacy or anonymity.
- We do not claim Windows ACL hardening, filesystem secure erasure, CI/release verification, or signed release provenance; local `cargo audit`/`cargo deny` gates for both lockfiles passed, and the M12/M13 redaction review with its path/error regressions is recorded in `PROJECT_STATUS.md`.
- We do not claim universal NAT traversal or that a direct connection proves the peer is the intended contact.
- We do not claim strong anonymity, metadata confidentiality, Tor/I2P/mixnet support, or unlinkability. Optional discovery and relays reveal metadata to user-chosen peers/operators.
- We do not promote mDNS, Kademlia, identify, relay, NAT, ping, or control observations to trusted contacts, fingerprint verification, capabilities, presence, receipts, or delivery.
- We do not claim a dedicated relay-safe file-key/transport design; file transfer is conservatively disabled on observed relayed paths even though Noise protects the framed content key from relay visibility. We do not claim metadata privacy from relays, which observe PeerIds, IPs, timing, and sizes.
- We claim application-message confidentiality and MLS group authentication for the tested two- and three-member `MlsConversation` API, its wire flow, the controller, the GUI path that renders decrypted text in memory only, and the in-memory ciphertext queue. We claim admin-only Add/Remove/Update, epoch exclusion of removed members, and all-member receipt state for the M9 flows described above. We claim bounded parent `CHN1` policy frames are MLS-authenticated, that channel policy is enforced locally by the admin/member rules, and that ready non-default text/receipts use a signed, bound derived MLS group in the tested P1d/P1e flows. We do **not** claim a complete cryptographic channel ACL for parent policy or default-channel traffic, or that an excluded member can never obtain parent-group ciphertext. We claim per-transfer file confidentiality, bounded chunking, hash integrity, ciphertext-only quarantine, narrow TXT/PNG/GIF structural validation, and a policy-gated, explicitly approved in-memory release path for the tested flows. Bounded redial and resource limits are implemented and tested as transport/scheduler behaviour only; they do not prove contact identity, reconnection success, or message delivery. File integrity and structural validation are not malware safety. We claim ciphertext-only queue persistence and authenticated restore of joined MLS groups, ready derived channel groups, bounded pending operations, receipts, and queued ciphertext when an encrypted vault session is attached; decrypted text and setup KeyPackages/Welcomes are not restored. We do not claim that the desktop app has an independent scanner result, general format/MIME parsing, plaintext-at-rest release, GUI/directory admin role delegation (P6 is a local primitive only), per-channel MLS keys for parent/default traffic, metadata privacy, or post-quantum support. We claim only partial local rollback detection: database-only rollback and anchor tamper are detected, but a full vault restored with its anchor is not, and no external anchor or replay-proof guarantee exists. The wire protocol advances delivery only on an explicit verified MLS receipt, setup completion only on a verified signed acknowledgement, file integrity only on a verified signed manifest and its acknowledgement, and scan/release status only on an actual independent scanner plus validated format, policy, and explicit approval. For M13 we claim only that optional capabilities are off by default, user-configured addresses are validated, relayed connections are bounded/observed, identify strings are bounded, control frames are opaque, and the privacy snapshot separates configuration from observed facts; we do not claim discovery trust, universal NAT traversal, anonymity, or file transfer over relays.
- We do not claim password recovery without backup material.
- We do not claim multi-device identity support in the initial release.
- We do not claim any feature is verified until its tests are recorded in `PROJECT_STATUS.md`.

## 9. Incident response and disclosure

Security issues should be reported privately before public disclosure. Once the project has a published repository/contact, add a `SECURITY.md` contact address at the repository root and a `security.txt`. Until then, record issues locally and do not publish exploit details. Locked local builds and both-lockfile advisory/policy gates passed in the final uncommitted state; historical CI results are not evidence for this workstream, and signed release identity/build provenance remain future work.
