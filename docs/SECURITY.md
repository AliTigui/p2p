# Security Policy and Threat Model

Status: Milestones 1–13 implemented and tested on this Linux host: local security, direct networking, MLS payload encryption, signed MLS setup and group control, the application controller, three bounded application wire protocols plus M13's opaque control protocol, the GUI send/receive path, reconnect-triggered ciphertext retry, bounded redial/backoff, honest retry state, duplicate-dial rejection, connection admission limits, per-peer request/byte budgets, admin-only multi-member Add/Remove/Update with pending acknowledgement state, group-wide delivery receipts, logical channels inside one MLS group with local membership policy, encrypted chunked file transfer, ciphertext-only quarantine with in-memory integrity verification, an independent scanner interface with exact result categories, dependency-free structural validation for TXT/PNG/GIF, a policy-gated in-memory release path, explicit per-file approval/cancellation, an encrypted attachment store, a native-only OS save flow, and explicit deletion policies, cross-platform safe export names, an unraisable release byte cap, safer native plaintext save, Unix symlink refusal for vault/quarantine paths, redacted transport-event `Debug`, bounded untrusted identity inputs, and optional M13 discovery, relay, NAT, identify, and control plumbing. Every M13 capability is off/empty by default; discovery candidates are advisory only and relays are user-operated. The desktop application configures no scanner, no allowed extensions, `Retain` quarantine deletion, and no optional network feature by default. General format/MIME parsing, a configured real scanner, MLS state persistence, admin role delegation, cryptographic per-channel keys, backup/restore, network-transfer cancellation, Windows ACL hardening, filesystem secure erasure, repository-wide log review, dependency advisory tooling, strong anonymity, metadata confidentiality, and universal NAT traversal remain out of scope or future targets. Security claims are only valid for features marked implemented and tested in `PROJECT_STATUS.md`.

## 1. Security invariants

1. No plaintext password, master key, identity private key, message content, or attachment key is written to disk or logs. Released file bytes stay in zeroizing memory until the user stores them encrypted or the native OS save dialog writes them to a user-chosen path; no other plaintext file is created.
2. All peer input is untrusted until verified: transport (Noise/PeerId), envelope (signature/version/replay), conversation (MLS), file (hash/format/scan/policy).
3. No core function requires a centralized service. Optional relay/DHT peers are user-operated and see ciphertext/metadata only. Every optional capability is off/empty by default; observations are advisory and never promote trust, contact verification, or delivery.
4. Delivery, verification, connection, and scanning statuses reflect observed facts; unknown states are shown as unknown.
5. Cryptographic failures fail closed: close stream, drop message, quarantine file, emit security event.

## 2. Threat model

| Threat | Mitigation | Status |
|---|---|---|
| Impersonation of a contact | Transport PeerId tied to Ed25519 key and authenticated by Noise; envelope signature binds the embedded public key to the declared PeerId; MLS BasicCredential and leaf signature key are checked against that envelope sender; fingerprint verification out of band | Transport implemented/tested (M4); envelope and MLS sender binding implemented/tested (M5); fingerprint implemented (M2) |
| Malicious relay reading messages | End-to-end MLS ciphertext protects message payloads and receipt bodies; a relay never receives message keys, private keys, or file keys; Noise protects the transport. M13 relay support is opt-in, user-configured, and bounded; file transfer is refused on observed relayed paths because the signed offer carries the fresh content key | MLS implemented/tested (M5); M13 relay config/events/policy implemented/tested locally, two-machine relay unverified |
| Replay of old messages | Bounded message-ID cache + strict per-sender sequence high-water mark + outer/MLS epoch equality checks; MLS verifies group-epoch authentication | Envelope replay implemented/tested (M5 core); MLS epoch/group checks implemented/tested (M5) |
| Offline password guessing | Argon2id 64 MiB/t=3/p=1, per-profile salt, bounded/versioned params | Implemented and tested (M3) |
| Local disk forensic recovery | AEAD ciphertext at rest for profile data, settings, message envelopes, and attachments; secure_delete; restricted directory permissions (0700/0600 on Unix); quarantined file ciphertext with no persisted transfer key; released bytes stay in zeroizing memory; native OS save is the only plaintext disk write and requires a user-chosen path | Implemented/tested for messages (M5), file quarantine (M7), release, encrypted attachments, and explicit deletion (M8), plus safe names, bounded inputs, and Unix symlink refusal (M12); filesystem deletion is not secure erasure on SSD/CoW storage |
| SQLite journal/temp leakage | Only ciphertext stored in sensitive columns; message, conversation, and attachment IDs are blind indexes; attachment keys are wrapped and metadata is encrypted; `temp_store=MEMORY`, `secure_delete=ON`, WAL contains ciphertext not plaintext | Implemented and tested (M3/M5/M8) |
| Malicious/malformed files | Signed offers, fresh per-transfer key, AEAD chunk bounds/AAD, manifest hash commitment, restricted ciphertext-only quarantine, no auto-execute; release requires valid TXT/PNG/GIF structure, an exact independent scanner result, name/size/count/extension policy, and explicit per-file approval. These validators are not general parsers or malware detection | Integrity/quarantine implemented/tested (M7); scanner interface, narrow format validation, approval/cancel, release gate, encrypted store, and explicit deletion implemented/tested (M8); general format/MIME parsing remains future work |
| DoS via many connections or huge frames | Transport connection timeout, bounded command/event queues, 1 MiB request/response frame cap, 8 concurrent message streams, 4 concurrent setup and 4 concurrent file streams, global/per-peer/per-IP connection caps, a separate relayed-connection cap/count, duplicate-dial rejection, shared sliding per-peer request/byte budgets, bounded identify strings, plus 64 MiB/256 KiB/256-chunk file bounds | Timeout/queues implemented (M4); frame/stream bounds implemented/tested (M5); connection and request budgets implemented/tested (M6); file bounds implemented/tested (M7); complete-file release policy implemented/tested (M8); M13 relayed-connection and bounded-control plumbing implemented/tested locally |
| Downgrade attacks | Noise-only transport (no plaintext feature); fixed `/p2p-messenger/message/1`, `/p2p-messenger/mls-setup/1`, `/p2p-messenger/file/1`, and M13's `/p2p-messenger/control/1` multistream protocols; versioned envelope/setup/file frames with fixed magic and unknown-version rejection | Transport implemented/tested (M4); application negotiation and frame versioning implemented/tested (M5/M7); M13 control codec implemented/tested locally |
| Forged or late MLS setup | `MLS1` frames are Ed25519-signed by the vault identity and checked against the Noise-authenticated PeerId; KeyPackage and Welcome bytes reach OpenMLS only after signature/peer verification; terminal-state guards reject late acknowledgements | Implemented/tested (M5) |
| Unauthorized or stale group change | Creator is the initial admin; only that authenticated PeerId may Add/Remove/Update. Signed commits are checked against sender, operation, target, MLS credential, and epoch. Commits stay pending until required acknowledgements; removed members keep the excluded epoch and stale epochs are rejected | Implemented/tested (M9); role delegation not implemented |
| Unauthorized channel policy or cross-channel text | Bounded `CHN1` bodies are inside authenticated MLS application content; only the admin may create/rename/set members, metadata revisions must advance sequentially, and text is accepted locally only from allowed MLS members. Invalid frames get no delivery receipt | Implemented/tested (M10); local policy only, not a cryptographic access-control boundary |
| Supply chain compromise | Cargo.lock, minimal dependency surface, locked CI builds, review before upgrades | Cargo.lock/locked builds implemented; `cargo-deny`/audit tooling remains future work |

No anonymity claim is made | M13 behaviour, bounded strings, and honest status implemented/tested locally; strong anonymity remains out of scope |
| Accidental secret logging | No secret `Debug` output; `zeroize` buffers; network errors truncated and kept non-secret; envelope, conversation, channel, file, released-file, and M12/M13 transport-event debug output omit ciphertext/key/plaintext bytes, and M13 bounds identify-provided strings | Implemented through M13 for covered view/debug types; repository-wide log review remains future work |

## 3. Network security implemented in Milestone 4

- Direct connect uses libp2p TCP + Noise + Yamux with the vault Ed25519 key imported through the stable protobuf Keypair encoding. The network PeerId matches the vault identity.
- Dial addresses must end in `/p2p/<peer-id>`; user-supplied bootstrap/relay addresses follow the same rule and must not contain `/p2p-circuit`. Noise authenticates that PeerId before a connection is reported; a wrong PeerId fails the handshake.
- No bootstrap peers, DHT, mDNS, identify, ping, relay, AutoNAT, DCUtR, UPnP, or developer-operated endpoints are configured by default. The default listen address is `/ip4/0.0.0.0/tcp/0`. M13 adds opt-in user-configured discovery/relay/NAT/identify behaviours; none is enabled or contacted in the default path.
- Connection status comes only from Swarm events. The GUI does not turn a button press into a "connected" indicator.
- `identify` is off by default. If explicitly enabled it hides listen addresses and bounds protocol/agent strings, but advertised protocol lists are still not cross-checked. A connected PeerId, discovery candidate, or identify result is not a fingerprint-verified contact.
- `/p2p-messenger/message/1`, `/p2p-messenger/mls-setup/1`, `/p2p-messenger/file/1`, and M13's `/p2p-messenger/control/1` are negotiated separately over the authenticated connection, each with a bounded 1 MiB request/response frame. Message `SentToPeer` never claims delivery; setup `SentToPeer` never claims group join; file `SentToPeer` never claims transfer completion; `ControlEvent::SentToPeer` never claims an application capability or receipt. Only verified application receipts and setup acknowledgements advance their states; only a verified file manifest acknowledgement advances file integrity status. M12/M13 hand-written `Debug` implementations for all four event types report identifier, peer, and byte length but never print opaque request or response bytes.
- MLS payload encryption, signed setup, and signed group-control frames are implemented for two- and three-member groups; a live connection still does not prove that the peer is the intended contact. M13's control protocol is opaque transport plumbing and carries no capability, presence, receipt, delivery, trust, or safety semantics.
- Direct peers see IP addresses, connection timing, and traffic sizes. Metadata privacy is not claimed.

### Milestone 6 network resilience

- A redial attempt is created only for an address the user explicitly supplied. Retry count and delay growth are capped, and a user disconnect suppresses redial until a fresh explicit dial. `RedialState` is scheduler intent, never a connection, delivery, or contact-verification claim.
- Duplicate pending dials are rejected until the first dial settles. Established connections are capped globally, per authenticated PeerId, and per observed IP; excess connections are closed.
- A shared sliding per-peer window caps inbound application request count and request bytes for all four bounded protocols before the application decodes them. Rejected requests produce honest transport failure events.
- These controls limit resource use; they do not authenticate the human behind a PeerId, prevent Sybil identities, hide metadata, or replace application-level authorization.

### Milestone 13 optional network privacy

- Every optional behaviour is configured off/empty by default and applied only when the network worker starts; changing settings requires lock/unlock. No developer-operated peer is compiled in.
- mDNS and Kademlia produce advisory candidate counts only. Kademlia requires user-supplied direct bootstrap addresses. Discovered peers are never auto-dialed, saved as contacts, trusted, or marked fingerprint-verified.
- Relay client/server modes require explicit user configuration and are bounded. Relay operators can observe IP addresses, timing, and sizes and can deny service, but they receive no private keys, message keys, or file keys. Relayed connections are separately capped and counted from observed `is_relayed()` connections; a relayed path is not a trust or delivery claim.
- Because the signed M7 file offer carries the fresh content key, `send_file` refuses to send over an observed relayed path until a separate end-to-end key exchange exists.
- AutoNAT and DCUtR are best-effort observations/hole-punch attempts, not universal NAT traversal. Ping is a low-frequency liveness observation, not application health or delivery. Identify hides listen addresses and bounds peer-provided strings, but still reveals a bounded protocol/agent description.
- `/p2p-messenger/control/1` uses the bounded opaque codec. The controller drains control, discovery, relay, NAT, and identify queues only to update the cached privacy snapshot; it never promotes an observation into a contact, verified peer, capability, receipt, or delivery state.
- `NetworkPrivacyStatus` separates local configured flags/counts from counters/strings updated by real libp2p events. The GUI shows limitation rows rather than claiming anonymity, universal connectivity, or file transfer over relays.
- Two-machine LAN, NAT, and volunteer-relay verification remains an external test. There is no Tor/I2P/mixnet support, metadata confidentiality, or unlinkability claim.

## 4. Messaging security implemented in Milestone 5

- Envelopes are canonical v1 records with fixed `P2P1` magic, version, conversation/message IDs, real MLS epoch, sender PeerId, embedded protobuf public key, sequence, untrusted timestamp, kind, MLS ciphertext payload, and a 64-byte Ed25519 signature over every field except the signature.
- The embedded public key is bound into the signature and checked against the declared PeerId. A PeerId is only a multihash and cannot verify a signature by itself. Decoding rejects wrong magic, unknown versions, bad kind codes, oversized fields, truncated fields, and trailing bytes.
- Incoming envelopes are verified before replay state is touched. Conversation mismatches, epoch mismatches, duplicate message IDs, and regressed sender sequences are rejected. The replay cache is bounded, with a strict per-sender sequence high-water mark.
- `MlsConversation` uses OpenMLS 0.9.2 with `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`. KeyPackage acceptance binds the expected PeerId bytes to the MLS BasicCredential and the expected raw Ed25519 public key to the leaf signature key. Welcome joining uses the original `MlsKeyPackage` provider so the in-memory private material is retained.
- On receive, MLS checks the group ID, epoch, member set, credential, and leaf signature key before returning plaintext. A valid envelope signed by a different peer over another member's MLS ciphertext is rejected. Decrypted bytes are held in a `Zeroizing` buffer and are not written to logs or the vault.
- Receipts use explicit `Delivered`/`Read` bodies, encrypted as MLS application messages. A receipt for an unknown message is rejected, and `SentToPeer` remains explicitly unconfirmed; no local send action creates a delivery claim.
- Envelopes are stored only as XChaCha20-Poly1305 ciphertext in schema v2 of the vault, with HMAC blind indexes for conversation/message lookup. Raw database/WAL/SHM sentinel scans cover message bytes. The legacy load path can reverify opaque envelopes, but MLS receipts cannot be rebuilt without MLS state; `MlsConversation` has no load path yet.
- MLS group state is memory-only: it is never written to disk in plaintext, but it is lost on restart. A valid signature authenticates control of the sender key; it does not prove the sender is the intended contact, so fingerprints must be compared out of band.
- `/p2p-messenger/message/1` uses libp2p request-response over Noise. The transport carries an opaque, bounded frame; it does not verify signatures or change delivery state. The application decodes and verifies envelopes before replay changes, and decrypts/verifies receipts before changing delivery state.
- `/p2p-messenger/mls-setup/1` carries signed `MLS1` frames. The signature binds the PeerId, public key, conversation ID, message code, and body; the controller checks the frame against the Noise-authenticated peer before passing KeyPackage or Welcome bytes to OpenMLS. The inviter waits for a verified `WelcomeAck` before showing `Joined`. No dedicated setup replay cache exists; status checks and terminal-state guards prevent late Welcomes/Acks from changing an established group, but a duplicate KeyPackageRequest can overwrite pending state.
- `MessengerController` keeps MLS groups, pending KeyPackages, decrypted text, and setup status in memory only. GUI delivery labels come from `DeliveryState::description()`; `ChatMessage::Debug`, `QueuedMessage::Debug`, and `SetupEnvelope::Debug` redact plaintext, ciphertext bodies, and setup bodies.
- The offline queue stores the signed MLS ciphertext envelope only, never the composed plaintext. It is not persisted, is lost on restart or lock, and is retried only after an observed `ConnectionState::Connected` event for that peer. Polling while disconnected cannot promote `Queued` to `SentToPeer`, and retry cannot promote to `Delivered` without a verified MLS receipt. A raw database/WAL/SHM scan asserts that no queued plaintext reaches the vault.
- Wire and controller acceptance tests send an MLS-encrypted signed envelope and an MLS-encrypted receipt between two isolated instances, and complete the signed setup exchange before that traffic. Re-signing tampered ciphertext is rejected by MLS, and a foreign sender envelope carrying another member's ciphertext is rejected by the MLS sender binding. Tampered setup frames and wrong-peer signatures are rejected before MLS state changes. The GUI path uses the same controller and does not create independent delivery claims.

### Milestone 9 group security

- Codes `5`–`10` extend the same signed `MLS1` codec with group join, KeyPackage, Welcome, commit, and acknowledgement frames. Strict parsers reject unknown operations, bad target encodings, empty commits, malformed acknowledgements, trailing bytes, oversized frames, and tampered signatures before MLS state changes.
- The creator is the initial admin. Only that PeerId may start Add, Remove, or self-Update. `check_admin` also requires a joined conversation and no pending operation. `add_member` requires a direct connection; `remove_member` denies self-removal and nonmembers.
- The admin merges a commit locally, broadcasts it to required existing members, and clears `pending_operation` only after the group Welcome and all required CommitAck frames are verified. Messages and further group changes are blocked while pending; disconnected required members can leave it pending until reconnect. No timeout, rollback, or partial completion is claimed.
- A new member joins at the Add commit's new epoch through its signed Welcome and is excluded from that commit's acknowledgement set, so it never applies the commit that created its epoch. The admin identity is learned from the signed Welcome sender after the join request exchange.
- MLS `process_commit` verifies the commit sender's signature/key and the declared operation/target before merging. Remove advances remaining members' epoch; the removed member stays on the excluded epoch and cannot decrypt future group traffic. Stale-epoch ciphertext from the removed member is rejected.
- Text is one signed MLS envelope broadcast to all current members with one ciphertext queue copy per disconnected recipient. Local `Delivered` requires verified receipts from every expected member; transport sends and partial receipts do not create a delivery claim.
- Admin authority is local client policy from signed frames, not a cryptographic role system. Role delegation, external commits, and encrypted MLS state restoration are not implemented. Setup/group-control frames have no dedicated replay cache; request correlation and state guards limit late or unexpected frames.

### Milestone 10 channel security

- Channels reuse the signed v1 envelope and MLS plaintext path. The bounded `CHN1` body carries `channel_id`, revision, and text/create/rename/set-members data inside the MLS application plaintext; no new wire protocol, envelope version, setup code, or MLS group was introduced.
- The outer envelope signature and MLS sender binding authenticate the writer. Strict decoding rejects wrong magic, unknown kinds, invalid PeerIds, empty/duplicate/oversized member sets, invalid names/text, truncation, trailing bytes, and oversized frames.
- The creator/admin alone may create, rename, or change channel membership. Create requires revision `1`; rename and member changes require the current revision plus one. Members must already belong to the MLS group. The default `[0; 16]`/`general` channel is present in every joined conversation and tracks current membership.
- Text is accepted from an authenticated MLS member who is also in that channel's local allowed set, and restricted sends go only to allowed recipients. Invalid or unauthorized frames receive no delivery receipt and only a static `last_error` category.
- Channel metadata changes do not create MLS commits. Their `acknowledged` state is derived from receipts for the last locally composed policy frame; custom channels are not replayed to later joiners.
- **Channels are not cryptographic access control.** Every MLS group member holds the group keys, so a member could decrypt a channel ciphertext it obtains. Restricted delivery reduces ordinary exposure but cannot provide a separate confidentiality boundary. Per-channel MLS keys are not implemented.
- Channel names/text are redacted from `Debug`, channel state is memory-only, and no plaintext channel body is written to disk by the controller.

## 5. File security workflow

Implemented in M7 and extended in M8:

- Sender: validate base name and bounded size → compute per-chunk and full SHA-256 → derive a signed manifest commitment → generate a fresh 32-byte content key → send it only inside the signed offer over the Noise-authenticated connection → encrypt each chunk with XChaCha20-Poly1305 and bound AAD → advance only on explicit signed acknowledgements. There is no network-transfer cancellation yet; release decisions can be cancelled per file.
- Receiver: verify the signed offer against the authenticated PeerId → create a `0700` quarantine directory → verify each signed chunk's AEAD tag in memory before writing ciphertext → verify the signed manifest against the commitment, every chunk hash, and the full SHA-256 → write only a hash manifest record to quarantine. Plaintext and the content key are never written to disk.
- The joined MLS conversation is required before a transfer starts, and only one transfer per peer is active. Integrity status comes from verified signed frames; transport sends and acknowledgements alone never mark a transfer complete.
- `IntegrityVerified` means byte-for-byte agreement with the signed hashes only. After verification and before scanning, `ScanStatus` is `Unavailable`; before verification it is `NotApplicable`. There is no `Clean`, `Safe`, or `Scanned` status produced by integrity checking.
- `p2p-security` defines an application-supplied `FileScanner` taking bounded in-memory bytes (`name` plus plaintext bytes) and returning one exact category: `CleanNoThreatDetected`, `ThreatDetected`, `Unavailable`, `Failed`, or `UnsupportedFormat`. `NoScanner`/default configuration returns `Unavailable` without inspecting bytes. The scanner never receives a disk path, and this interface writes no plaintext.
- Only `SecurityConfig::scan` can create a `ScanOutcome`; the private outcome and format fields prevent an application caller from fabricating a clean result or validated format. `SecurityConfig::scan` first checks the claimed extension against the bytes; a mismatch short-circuits to `UnsupportedFormat` before an independent scanner is invoked. `p2p-chat::scan_file` reassembles plaintext only in a zeroizing buffer, invokes the configured scanner, and stores the exact category and validated format on the transfer. With no scanner configured, a supported format records `Unavailable`; a mismatch records `UnsupportedFormat`.
- Structural validation is dependency-free and deliberately narrow: UTF-8 text without disallowed control bytes, PNG signature/chunk/CRC/IHDR/IEND structure, and GIF header/block/trailer structure. It is not malware detection, a general media parser, or a MIME sniffer.
- `ReleaseApproval` moves a transfer from `NotReady` to `Pending` only after a clean scan, validated format, cross-platform safe base name, non-empty bounded size/chunk count under an unraisable 64 MiB cap, and explicit extension allowlist. `approve_file` records the user's explicit decision; `release_file` still requires `Approved` and returns plaintext only in a zeroizing `ReleasedFile` buffer. `cancel_file` is terminal for release, does not delete ciphertext, and does not cancel the network transfer. Default policy allows no extensions, so every release is denied by default. Release does not write plaintext to disk and does not call anything safe or clean.
- Extension checking alone is never treated as format validation. A clean antivirus result is defence in depth, never a guarantee.

M8 release/storage boundary: `ReleasedFile` is copied by the desktop application into an encrypted attachment store with a random per-file key, blind index, encrypted metadata, and a digest recheck on read. The native-only OS save dialog is the only plaintext disk write and requires a user-chosen path; a cancelled dialog writes nothing. M12 sanitizes the suggested name, refuses a pre-existing symlink, creates the file as `0600` on Unix, syncs before returning, and reports only static errors. Stored-attachment deletion is explicit; M12 checks blob paths for symlinks before removing the database record. Quarantine deletion defaults to `Retain`; under `Explicit` it requires a verified transfer that was released or cancelled. Neither deletion action implies the other, grants a clean status, cancels the network transfer, or guarantees secure erasure on SSD/CoW storage.

Still not implemented: general format/MIME parsing, network-transfer cancellation, backup/restore, and a configured real scanner. Until a real scanner returns `CleanNoThreatDetected` for a structurally validated file, the UI must say **"Scanning unavailable"** and no release path may succeed.

## 6. Local storage and privacy

- Sensitive fields are AEAD ciphertext before they reach SQLite. Blind indexes (HMAC with a dedicated subkey) are used where lookups are required. Implemented for the profile vault and settings in M3 and message envelopes in M5, including raw database/WAL/SHM sentinel scans.
- Search indexes are a design target: any future index must use encrypted/keyed lookups, and plaintext full-text indexes will not be used. No search index exists yet.
- M7 quarantines incoming ciphertext in `0700` directories with `0600` chunk files on Unix (Windows ACL hardening remains a target). M8 attaches released bytes only as encrypted blobs with encrypted metadata; the native-only OS save dialog writes plaintext solely to a user-chosen path and writes nothing if cancelled. M12 refuses symlinked final paths when opening a vault or creating a quarantine directory on Unix, checks attachment blob paths for symlinks before record deletion, and hardens the save helper described above. Stored attachments and quarantine ciphertext are deleted only by separate explicit actions; filesystem deletion is not secure erasure on SSD/CoW storage.
- Encrypted backups with a separate recovery passphrase and an encrypted identity export are a design target. No backup/restore code or UI exists yet.

## 7. Logging policy

Log: protocol versions, PeerIds (public), connection state transitions, error categories, transfer IDs, security event categories. Never log: passwords, derived keys, private keys, message plaintext, attachment bytes, full file paths where not needed, QR payloads containing private material (they never do). Setup and group-control `Debug` output reports body lengths and redacts KeyPackage, Welcome, and commit bytes. Channel frame and `ChannelInfo` `Debug` output redacts channel names and text. M12 transport event `Debug` output redacts message, setup, and file request/response bytes; M13 extends that to control frames and bounds identify-provided strings; static failure reasons and public identifiers remain. M12 also rejects oversized contact URIs and identity envelopes before decode/KDF work so hostile inputs cannot turn into verbose structured errors. Debug builds must not print secret buffers; use `zeroize` and avoid `Debug` derives on secret wrappers. A repository-wide log review is still future work.

## 8. What we explicitly do not claim

- We do not claim antivirus scanning proves a file is safe.
- We do not claim metadata privacy or anonymity.
- We do not claim Windows ACL hardening, filesystem secure erasure, repository-wide log review, or dependency advisory tooling; the M12 controls are the bounded, tested subset recorded in `PROJECT_STATUS.md`.
- We do not claim universal NAT traversal or that a direct connection proves the peer is the intended contact.
- We do not claim strong anonymity, metadata confidentiality, Tor/I2P/mixnet support, or unlinkability. Optional discovery and relays reveal metadata to user-chosen peers/operators.
- We do not promote mDNS, Kademlia, identify, relay, NAT, ping, or control observations to trusted contacts, fingerprint verification, capabilities, presence, receipts, or delivery.
- We do not claim end-to-end file keys over relays; file transfer is disabled on observed relayed paths.
- We claim application-message confidentiality and MLS group authentication for the tested two- and three-member `MlsConversation` API, its wire flow, the controller, the GUI path that renders decrypted text in memory only, and the in-memory ciphertext queue. We claim admin-only Add/Remove/Update, epoch exclusion of removed members, and all-member receipt state for the M9 flows described above. We claim bounded `CHN1` text and policy frames are MLS-authenticated inside one group, that channel policy is enforced locally by the admin/member rules, and that restricted channel text is sent only to allowed recipients for the tested M10 flows. We do **not** claim channel membership is cryptographic access control or that excluded group members cannot decrypt channel ciphertext they obtain. We claim per-transfer file confidentiality, bounded chunking, hash integrity, ciphertext-only quarantine, narrow TXT/PNG/GIF structural validation, and a policy-gated, explicitly approved in-memory release path for the tested flows. Bounded redial and resource limits are implemented and tested as transport/scheduler behaviour only; they do not prove contact identity, reconnection success, or message delivery. File integrity and structural validation are not malware safety. We do not claim that the desktop app has an independent scanner result, general format/MIME parsing, plaintext-at-rest release, queued-message persistence, MLS state restoration after restart, admin role delegation, per-channel MLS keys, metadata privacy, or an encrypted MLS persistence layer. The wire protocol advances delivery only on an explicit verified MLS receipt, setup completion only on a verified signed acknowledgement, file integrity only on a verified signed manifest and its acknowledgement, and scan/release status only on an actual independent scanner plus validated format, policy, and explicit approval. For M13 we claim only that optional capabilities are off by default, user-configured addresses are validated, relayed connections are bounded/observed, identify strings are bounded, control frames are opaque, and the privacy snapshot separates configuration from observed facts; we do not claim discovery trust, universal NAT traversal, anonymity, or file transfer over relays.
- We do not claim password recovery without backup material.
- We do not claim multi-device identity support in the initial release.
- We do not claim any feature is verified until its tests are recorded in `PROJECT_STATUS.md`.

## 9. Incident response and disclosure

Security issues should be reported privately before public disclosure. Once the project has a published repository/contact, add a `SECURITY.md` contact address at the repository root and a `security.txt`. Until then, record issues locally and do not publish exploit details. Locked builds are checked in CI; automated dependency advisories remain future work.
