# System Architecture — Decentralized P2P Encrypted Messenger

Status: **v0.1 design baseline; Milestones 1–13 remain implemented, and the P0–P14 hardening plus Q0/Q1/Q2/Q5 workstreams were completed in historical pre-v3 local runs.** The current production application wire is P2P3 `EnvelopeV3` with signed setup v4 over `/p2p-messenger/mls-setup/2` and the pinned hybrid MLS suite `0x004F`; Q3 (v3 metadata reduction) and Q4 (bounded wire-level deniability) are complete locally/uncommitted. A historical pre-v3 serialized run reported 358 workspace tests and 22 GUI-feature tests; those counts are not current, and current final gate results are recorded in `PROJECT_STATUS.md` and `SECURITY_TESTS.md`. Historical runs also covered fmt, `git diff --check`, diagnostics (64 Rust sources), workspace/GUI/native checks, both-lockfile audit/deny, fuzz checks, smoke runs, and SBOM regeneration. This closeout includes the post-M13 schema-v4 control log/anchor, ADR-0014 Phases 1–4 encrypted storage and restore, P2–P13 role-separated identity, replay/persistence hardening, fail-closed transport configuration, local delegation primitives, native file picking, a bounded ciphertext-only offline queue, historical pre-v3 classical-only OpenMLS evaluation and signed-envelope metadata non-claims (superseded by the hybrid suite and v3 wire), portable encrypted bundles, supply-chain gates, hostile-peer bounds, Q1 relay-only routing, Q2 fixed-bucket MLS padding, and Q5 SOCKS5-only routing. P14 is verification and limitation consolidation only; it creates no Milestone 14. Q3/Q4 are complete locally/uncommitted; Q4 is bounded wire-level deniability, not ephemeral delegated keys. M13 optional discovery, relay, NAT, identify, and control capabilities remain off/empty by default. All claims here are local-only for uncommitted work: no CI, release, commit, push, PR, review, merge, user/manual, external, two-machine, visual-GUI, or production-readiness claim is made. This document describes the target architecture and marks which parts are implemented; `PROJECT_STATUS.md` and `SECURITY_MILESTONE_REPORTS.md` record historical local evidence; `PROJECT_STATUS.md` and `SECURITY_TESTS.md` record current final gate results.

## 1. Non-negotiable constraints

1. **No mandatory centralized server.** No developer-operated bootstrap node, signaling server, identity server, account database, message relay, or cloud storage is required for any core function.
2. **Two installations must be able to communicate with nothing but each other's addresses.** Manual address/QR exchange is a first-class, fully functional mode.
3. **Users own their identities and data.** Identity keys are generated locally, encrypted at rest, and exportable. No hardware identifiers are used.
4. **All user content is end-to-end encrypted.** Relay/discovery peers may carry ciphertext and metadata only.
5. **Established protocols and primitives only.** MLS (RFC 9420) via OpenMLS for conversations, including the pinned hybrid KEM suite `0x004F`; libp2p Noise for transport; Argon2id + XChaCha20-Poly1305 for local key protection. P2P3 composes MLS exporters, XChaCha20-Poly1305, and HMAC-SHA256 with no custom primitive; MLS signatures and Noise remain classical, so this is not post-quantum.
6. **Fail closed and report honestly.** Unimplemented, unavailable, or failed operations must be shown as such. No fake "connected", "delivered", "verified", or "scanned clean" states.

Consequences of these constraints are recorded in `docs/DECISIONS/`.

## 4. Runtime model

- **GUI event loop**: egui/eframe describes panels and widgets. It never performs crypto or blocking I/O; only the current view model is rendered.
- **Typed app facade**: Rust functions called directly from the GUI validate inputs and return typed errors. No network operation is awaited from the GUI thread; long operations run on dedicated workers and deliver events to the view model.
- **Tokio runtime**: the Milestone 4 network worker owns a Tokio current-thread runtime on its own `std::thread`; it owns one libp2p `Swarm` per local identity per process. A future shared application runtime may add dedicated message and file-transfer workers; today `p2p-chat` drives both workflows through the network worker.
- **Blocking pool**: Argon2id derivation, filesystem I/O, and SQLite calls use a dedicated `std::thread` per vault operation today, so the UI never blocks. File reads and writes are short bounded operations driven from `poll`; they will move to a shared Tokio blocking pool as the runtime model expands.
- **Local database**: single writer connection, WAL journal, all sensitive values stored as AEAD ciphertext written by the storage layer. Schema v4 keeps an encrypted, chained digest log in `control_log`/`control_state` and an AEAD-protected high-water mark in the vault directory's `control.anchor` (atomically replaced via `control.anchor.tmp`); unlock verifies records, chain, blind indexes, and anchor, detecting partial (database-only) rollback. Schema v5 adds ADR-0014 Phase 1 `mls_groups`/`mls_state` opaque-value rows under versioned `Purpose::Db` AAD with `Purpose::BlindIndex` indexes and per-group SHA-256 chains; Phase 2 extends the anchor to v2 with authoritative per-group watermarks, so unlock verifies the exact watermark map and detects database-only rollback of the MLS tables. Transfer ciphertext lives in a restricted quarantine directory; the content key is memory-only. M8 scanner input, released plaintext, and OS-save decryption stay in zeroizing memory buffers. Released files are copied into the encrypted attachment store; the only plaintext disk write is the user-initiated native OS save to a chosen path. Phase 4 writes joined-group policy, pending operations, receipt expectations, and queued ciphertext into the same encrypted MLS-state namespace under the group blind index; P1e adds separate authenticated `p2p.app.channel-group/v1` records under derived group IDs; no plaintext index or queue table is created.

Channels between UI and workers are typed `mpsc` queues for vault results, connection state, message events, setup events, file events, control events, and M13 discovery/relay/NAT/identify observations. The network worker reports `SentToPeer`, `RequestReceived`, `ResponseReceived`, and `Failed` for all four bounded protocols and advisory privacy events; it never declares delivery, group join, file integrity, trust, or a fingerprint-verified contact. State transitions are owned by `p2p-chat`/`p2p-messaging`/`p2p-groups`/`p2p-files`; the UI is a projection and never the source of truth. M13 observations update only a cached `NetworkPrivacyStatus`; no application capability follows from them.

## 5. Key hierarchy (implemented in Milestone 3)

```
OS CSPRNG
   ├── libp2p Ed25519 identity keypair ──> PeerId (public, shareable)
   │                                   └──> credential signing key for MLS
   └── master key (32 bytes, random)  ──> Argon2id KEK wraps it in an envelope
                                          └── HKDF-SHA256 domain-separated subkeys
                                                ├── storage/db
                                                ├── storage/attachments
                                                ├── storage/identity
                                                ├── storage/search-index
                                                ├── storage/blind-index
                                                └── storage/backup
```

The password derives only the key-encryption key (KEK). Changing the password re-wraps the master key; no application data is re-encrypted. Losing both password and recovery material means permanent data loss — there is no escrow. Argon2id parameters are bounded before any derivation, and the KDF id, salt, and parameters are bound into the wrapped-key AAD so they cannot be downgraded unnoticed. A dedicated `storage/blind-index` subkey powers HMAC lookups. Schema-v4 control records and the vault anchor are AEAD-encrypted under `Purpose::Db` with profile-bound AAD; their blind indexes use `Purpose::BlindIndex` and never the AEAD key. ADR-0014 Phases 1–3 MLS-state rows and the v2 anchor use the same division of keys with record-version/profile/group/entity/epoch-bound AAD and a separate anchor-version AAD label; a dedicated `Purpose::MlsState` is deferred because it would require a stored-salt-slot migration.

## 6. MLS setup and message lifecycle (Milestones 5, 6, and 9; current v3/v4 wire)

Implemented and tested through the Rust controller and GUI:

```
connected peer supplies a Peer ID (address and fingerprint verified out of band)
  → inviter creates an in-memory MlsConversation and signed v4 KeyPackageRequest
  → /p2p-messenger/mls-setup/2 over Noise (SentToPeer is not Joined); ciphersuite_id bytes 6..8 = 0x004F
  → responder verifies signed v4 frame/PeerId, generates MlsKeyPackage, signs KeyPackageResponse (v1–v3 setup and unknown suites rejected)
  → inviter verifies response, calls add_member, signs v4 Welcome
  → responder joins with OpenMLS hybrid suite, signs WelcomeAck (accepted or rejected)
  → inviter records Joined only after verifying the accepted WelcomeAck

plaintext application bytes
  → OpenMLS encrypt into the conversation's current member group (hybrid 0x004F; Ed25519 signatures)
  → wrap MLS ciphertext with XChaCha20-Poly1305 under a purpose-separated MLS exporter key and assemble V3InnerFrame (sender/proof/role key, conversation, MLS epoch, message ID, sequence, timestamp, kind, receipt body)
  → compose P2P3 EnvelopeV3: V3_MAGIC/version, 32-byte route tag = SHA-256(domain separator || group ID || epoch), random nonce, wrapped MLS body, HMAC-SHA256 tag under another exporter key
  → broadcast once to every current member over /p2p-messenger/message/1 (no third-party-verifiable long-term application signature)
  → if connected: hand to the protocol (SentToPeer, not delivered); if disconnected: hold one ciphertext copy per recipient in the queue (Queued), retry only after a new Connected event
  → each recipient resolves the route tag locally (zero/ambiguous: UnknownMessageRoute/AmbiguousMessageRoute; wrong tag: BadRouteTag) and verifies the HMAC
  → each recipient unwraps the exporter-encrypted body, OpenMLS-decrypts with group authentication, then recovers V3InnerFrame and checks conversation/epoch/message-ID/sequence
  → each recipient composes an MLS-encrypted, v3-wrapped delivery/read receipt response
  → sender decrypts/verifies all expected receipts, then state: SentToPeer → Delivered/Read
  → persist envelope as XChaCha20-Poly1305 ciphertext in the vault (legacy v1/v2 envelopes are test-only)
```

The controller renders decrypted messages and delivery descriptions in the native GUI. For groups it broadcasts one P2P3 `EnvelopeV3` to all current members, keeps one queue entry per disconnected recipient, and promotes a local message to `Delivered` only after all expected receipts. The offline queue holds only v3 ciphertext (historically a signed envelope before v3), is retried from the observed-connection path, and is encrypted/restored through the vault when a session is attached; decrypted text is never persisted. Bounded redial uses only saved user-supplied addresses and reports scheduler intent separately from observed connection state; duplicate dials, excess connections, and excess per-peer requests are rejected. M9 admin-only Add/Remove/Update commits and acknowledgement state are implemented. M10 channels use the existing `MessageKind::Channel` envelope and a bounded `CHN1` MLS application body; channel selection filters the local decrypted view. P1d keeps create/rename/member policy in the parent MLS group but encrypts non-default channel text and receipts in a derived `MlsChannelGroup` with its own membership, epoch, and readiness receipts; the default channel remains on the parent group for compatibility. ADR-0014 Phase 4 wires the provider into the controller: joined MLS group state, channel policy, bounded pending operations, receipt expectations, channel acknowledgement state, and offline queued ciphertext restore with fail-closed validation; no restored state fabricates `Delivered`. Not implemented yet: read-receipt UI, setup KeyPackage/Welcome restoration, decrypted-message restoration, role delegation, and a complete channel ACL covering parent policy/default traffic. P1d's cryptographic boundary applies only to non-default text; P1e preserves ready derived groups across restart with fail-closed validation, and P1f reports that boundary separately from parent policy without claiming a complete ACL.

The legacy pre-v3 `Conversation::load` path (v2 test artifact) can reverify opaque envelope records but parses receipt bodies from raw payload bytes; it is not a restore path for MLS receipts, and legacy v1/v2 application envelopes are rejected on production paths. Runtime `MlsConversation` group state and channel metadata now restore from the encrypted provider/application record when a vault session is attached; pending setup KeyPackages, setup Welcome material, and decrypted text remain memory-only and are lost on restart. ADR-0014 Phases 1–3 store opaque provider values as authenticated ciphertext with anchor watermarks and expose a staged `StorageProvider`; Phase 4 calls it from the controller and restores bounded pending/receipt/queue state from an authenticated application record. The schema-v4 control digest log records only SHA-256 digests of already authenticated v4 signed setup/group-control frames and a repeatability flag; **the digests do not restore MLS state** (group/ratchet state, pending key packages, channels, or plaintext). Relays see outer libp2p ciphertext plus IP, timing, direction, volume, coarse outer length, and epoch-bound route-tag linkability, but no application plaintext. OpenMLS provides group authentication and epoch separation in the implemented setup; M9 Update/Remove commits advance epochs and exclude removed members, and Phase 4 preserves those epochs across restart without replaying old control frames. Timestamps are sender-supplied and displayed as such, never trusted for ordering. `SentToPeer` is not `Delivered`; the GUI shows the exact `DeliveryState::description()` instead of inventing a status.

### Durable control decisions (post-M13, not a new milestone)

- `MessengerController::start_with_control_log` accepts a cloned vault `Session` from `Session::try_clone`; the GUI uses this path. The controller identity must match the session identity, or startup fails with `ControlLogIdentityMismatch`. Controllers started without a session keep only the bounded in-memory setup/group digest cache.
- Schema v4 transactional migrations add `control_log (sequence, record_bi, ciphertext, chain_hash)` and `control_state (id, sequence, chain)`. Records contain only public PeerId bytes, a SHA-256 digest of an already authenticated v4 signed setup frame, and a repeatable flag. XChaCha20-Poly1305 under `Purpose::Db` with profile-bound AAD protects the records and the vault-directory `control.anchor` high-water mark; the latter is atomically replaced through `control.anchor.tmp`. HMAC indexes under `Purpose::BlindIndex` support lookup, and SHA-256 chaining links records.
- `KeyPackageRequest` and `GroupJoinRequest` are idempotent/repeatable; Welcomes, responses, commits, and all acknowledgements are non-repeatable. The log is bounded at 4,096 records and fails closed when full. `Vault::unlock` verifies records, chain continuity, blind indexes, and anchor before returning a session.
- A database-only rollback (with a current anchor) and an altered or missing anchor are detected as rollback. Restoring the entire vault including the anchor is not locally detectable; there is no external anchor, and this mechanism is not a backup. This is partial rollback detection, not a general replay-proof protocol.
- The ADR-0013 control log introduced no wire-format change at the time; the later v3/v4 application wire is a separate change. The local control log is unrelated to the M13 `/p2p-messenger/control/1` opaque control protocol, which carries no application semantics. `docs/DECISIONS/ADR-0013-durable-control-log-and-anchor.md` records the durable-control-log/anchor decision.

### Encrypted MLS state, anchor, and provider (ADR-0014 Phases 1–3, not a new milestone)

- Schema v5 adds `mls_groups`/`mls_state`: opaque provider values are XChaCha20-Poly1305 ciphertext under versioned `Purpose::Db` AAD, with HMAC blind indexes under `Purpose::BlindIndex`, per-group SHA-256 chains, and bounded CRUD (`1 MiB/value`, `4096` rows, `64` groups).
- Phase 2 extends `<vault>/control.anchor` to a version-2 AEAD record under a new versioned AAD label, keeping the control-log sequence/chain and adding a bounded, authoritative `group_blind_index -> (epoch, state_chain)` map. A v1 anchor is migrated on unlock after both databases verify.
- `Vault::unlock` verifies every MLS row, epoch binding, blind index, group chain, and the exact anchor watermark map before returning a session. A database-only rollback before an MLS write or deletion, an authenticated-but-mismatched anchor, or a missing required group fails with `RollbackDetected`. MLS writes install the anchor before committing so an interrupted write fails closed; control-log appends remain database-first with bounded anchor catch-up. Restoring the whole vault including the anchor remains undetectable.
- Phase 3 adds `StagedMlsProvider`, a vault-backed `openmls_traits::StorageProvider<CURRENT_VERSION>` adapter. It stages writes in memory for one MLS operation, exposes staged values to reads, discards on error or cancellation, and flushes the whole set as one SQLite transaction with anchor advancement and same-transaction tombstones. A real `MlsGroup::new_with_group_id` / `MlsGroup::load` round trip after reopening the vault is covered by `crates/storage/tests/mls_provider.rs`. Group-scoped methods reject reserved or non-16-byte group ids before staging; global provider entries use a reserved sentinel group id and draft virtual-client/extension methods remain unimplemented.
- Phase 4 uses this provider from the controller with an attached vault session: explicitly `Joined` MLS groups, encrypted channel policy, bounded pending operations, receipt expectations, channel acknowledgement state, and offline queued ciphertext are restored with fail-closed validation, and failures become a real GUI `Failed` state. The hardening pass rejects cross-profile/identity mismatches, prunes removed-peer receipt/queue state, and stores encrypted per-request outcomes so byte-identical group-commit and group-Welcome retries after restart return the original ack without a second MLS transition. Setup KeyPackage/Welcome restore, general frame replay protection, decrypted-message restore, and crash recovery for an anchor-first write remain out of scope.

## 7. Groups and channels (M9 group management, M10 channels, and P1d non-default text routing implemented)

- Implemented now: one parent MLS group per conversation, with a 2-member group for 1:1, plus separate derived `MlsChannelGroup` instances for non-default channel text; KeyPackage generation and binding, Add + Welcome join, encrypted text/receipts, epoch tracking, and rejection of tampered ciphertext or sender/credential mismatch. The signed v4 wire setup exchange over `/p2p-messenger/mls-setup/2` drives these calls through `p2p-chat` without out-of-band API handoff. There is no separate 1:1 encryption path to audit.
- M9 group control: codes `5`–`10` of the signed setup codec (historical `MLS1`, now signed v4 over `/p2p-messenger/mls-setup/2`) carry group join requests, KeyPackage responses, Welcomes, commits, and acknowledgements. The creator is the initial admin; admin-only Add/Remove/self-Update operations merge the commit locally, broadcast it to required existing members, and remain pending until the Welcome and required CommitAck frames are verified. A joining member receives the new epoch through the Welcome and is excluded from that Add commit's acknowledgement set. Removed members stay on the excluded epoch and cannot read future group messages.
- M9 delivery: one P2P3 `EnvelopeV3` per message goes to all current members. A ciphertext copy is held per disconnected recipient; `Delivered` requires receipts from every expected member. Messages and new group operations are blocked while an operation is pending, and pending commits are retried on reconnect.
- M10 channels (historical pre-v3): bounded `CHN1` frames are MLS application bodies inside the existing `MessageKind::Channel` envelope, now carried in a v3 protected inner frame. `channel_id` is part of the authenticated application content; M10 added no envelope version, setup code, MLS group, or transport protocol at the time, while Q3 later replaced the canonical application envelope with v3 and Q4 superseded transferable signed-envelope authorship. Every conversation starts with `[0; 16]`/`general`. The admin creates, renames, and sets members of channels; allowed members post text, which is sent only to allowed recipients. P1d changes the text path: policy metadata remains local application policy in the parent group, while non-default text and receipts are encrypted in a derived group whose membership is set by signed setup frames; channel sends wait for welcome and required commit acknowledgements.
- Channel metadata revisions are locally verified and receipt-gated for acknowledgement; invalid or unauthorized frames get no receipt. Custom channels are not replayed to later joiners, who receive the default channel. Encrypted channel/group-state restoration is implemented for explicitly `Joined` groups with an attached vault session. Target, not implemented: admin role delegation/changes, persistence of per-channel setup material, parent policy metadata confidentiality, and decrypted-message restoration. Ready per-channel MLS groups now restore from authenticated records, and the GUI reports the derived-group boundary separately from parent policy/default traffic.

## 8. File sharing, quarantine, policy-gated release, and encrypted storage (M7–M8 implemented)

Implemented and tested through `p2p-files`, `p2p-network`, `p2p-chat`, and the native GUI:

```
joined MLS conversation with authenticated Noise peer
  → sender validates base name, non-empty size ≤ 64 MiB, and ≤ 256 chunks
  → SHA-256 per chunk and over the full plaintext; signed manifest commitment
  → fresh 32-byte content key carried only in the signed offer over Noise
  → sequential 256 KiB XChaCha20-Poly1305 chunks with bound AAD and signed acks
  → receiver writes ciphertext to a 0700 quarantine directory (0600 files on Unix)
  → receiver decrypts in zeroizing memory, checks every chunk hash and full hash
  → signed ManifestAck; both sides report IntegrityVerified, not scanned
  → optional scan_file: validate claimed TXT/PNG/GIF structure, then re-assemble plaintext only in zeroizing memory and call app-supplied FileScanner
  → exact ScanResult category and validated FileFormat stored on the transfer; no scanner means Unavailable; mismatch means UnsupportedFormat
  → approval becomes Pending only after clean scan + validated format + name/size/count/extension policy
  → inactivity deadline or abort_file terminates only an active transfer
  → explicit per-file approval, then release_file; cancel_file is terminal for release
  → ReleasedFile is returned in zeroizing memory; the release path writes no plaintext
  → desktop app copies ReleasedFile into the schema v3 encrypted attachment store
  → native OS save decrypts into a zeroizing buffer and writes plaintext only to a user-chosen path
  → stored-attachment deletion and quarantine deletion are separate explicit actions; quarantine defaults to Retain
```

Integrity verification proves byte agreement with the signed manifest only. Structural validation checks a deliberately small set of formats and is not malware detection or a general media parser. `ScanStatus` is `NotApplicable` before verification and `Unavailable` afterward until `SecurityConfig::scan` actually invokes an independent scanner; no integrity check creates a clean status. A format mismatch short-circuits to `UnsupportedFormat` before the scanner sees bytes. A transfer starts only for a joined MLS conversation, and only one transfer is active per peer. `ScanOutcome` keeps both status and validated format private, so only `SecurityConfig::scan` can create a result that permits release. The default release policy allows no extensions, so release is denied even if a test scanner returns a clean category. An active transfer has a 5-minute default inactivity deadline (configurable up to 1 hour, reset by authenticated progress); timeout or `abort_file` marks it failed, drops pending response bookkeeping, zeroizes the in-memory key, and removes incomplete quarantine ciphertext. `cancel_file` is separate and applies only to an integrity-verified transfer whose verified ciphertext it retains. The pinned request-response API cannot withdraw a worker request already in flight, so abort ignores late responses rather than cancelling worker state.

The encrypted attachment store keeps a blind index, a wrapped random per-file key, and encrypted name/size/digest/format metadata in SQLite; the blob contains only XChaCha20-Poly1305 ciphertext. Reads recheck SHA-256 into a zeroizing buffer. The native-only OS save dialog is the only plaintext disk write and requires a user-chosen path; a cancelled dialog writes nothing. `QuarantineDeletionPolicy::Retain` is the default; under `Explicit`, deletion requires a verified transfer that was released or cancelled. Neither stored-attachment deletion nor quarantine deletion grants a clean status, aborts an active transfer, or guarantees secure erasure on SSD/CoW storage. Filesystem ACL hardening on non-Unix platforms remains a target.

Still absent: general format/MIME parsing, auto-execution policy, transport-level cancellation of an in-flight worker request, backup/restore, and a configured real scanner. No "clean" result may be invented before an independent scanner exists.

## 9. Offline behaviour

- Offline users: `Queued (offline)` is implemented for a joined MLS session. `send_text` composes one P2P3 `EnvelopeV3` (consuming the inner sequence only after a successful compose; no long-term application signature), stores only ciphertext, and the controller retries that exact envelope only after a real `Connected` event for the peer. `SentToPeer` remains unconfirmed and `Delivered` still requires a verified receipt. The vault-backed queue is encrypted and survives restart; without a session it stays memory-only, and decrypted text is never persisted. Bounded redial may produce a new observed `Connected` event, but its state is honest scheduler intent and is never shown as a live connection or delivery claim.
- DHT/relay peers are optional and user-operated. If a recipient is offline and no voluntary store-and-forward peer exists, delivery waits; the application does not silently route through developer infrastructure.
- Implemented connection state is derived from actual Swarm events: `Unknown`, `Starting`, `Listening(addresses)`, `Connecting(peer)`, `Connected(peers)`, `Disconnected(peer)`, and `Failed(peer, reason)`. `Offline`, `Discovering`, `Reconnecting`, and `Degraded (relayed)` are future states and are not shown as if observed today. `RedialState` is separate scheduler intent, not an observed connection state.

## 10. Platform strategy

- One native Rust GUI across Linux, Windows, and macOS using egui/eframe with the glow renderer. No webview, browser engine, Node.js, or npm is shipped or required.
- The `native` Cargo feature adds the OS window; the `gui` feature only describes widgets and compiles without display libraries, enabling CI/core verification anywhere.
- SQLite is bundled (`libsqlite3-sys` `bundled`) to avoid system version drift.
- Secrets use OS secure storage where available (planned: keychain/credential manager for the envelope key wrapper); otherwise the Argon2id-encrypted envelope in a 0700 app-data directory.
- Received files live outside the application executable directory.
- Installers: AppImage/DEB/RPM, MSI/EXE, DMG. Signing and notarization are release-engineering tasks tracked in Milestones 11–12.

## 11. Metadata and privacy hardening (M13, implemented)

- The zero-infrastructure direct path is unchanged: no bootstrap, DHT, relay, account, signaling, identify, or discovery service is needed. Defaults are off/empty for identify, ping, mDNS, Kademlia, relay client/server, AutoNAT, DCUtR, bootstrap addresses, and relay addresses.
- Optional behaviours are startup-only `Toggle`s/configuration in the network worker. The GUI exposes opt-in fields and applies them when `start_chat()` creates the worker; changing them requires lock/unlock. No network operation runs on the UI thread.
- mDNS and Kademlia emit advisory candidates/route counts only. Kademlia needs user-supplied direct bootstrap peers. No candidate is auto-dialed, saved as a contact, trusted, or treated as fingerprint-verified.
- Relay client/server modes require user-supplied direct relay addresses ending in `/p2p/<peer-id>`; relay-server circuits and relayed connections are separately bounded. Explicit server mode enables the relay HOP status with concrete external addresses; wildcard listens are not advertised. With pinned libp2p 0.57.1, relays forward Noise-protected opaque bytes: they see PeerIds, IP, timing, direction, volume, coarse outer length, and route-tag linkability within one epoch and can deny service, but they never receive application plaintext, private keys, message keys, or file keys. Q1 relay-only policy rejects direct dials/listeners and requires an observed relayed path. File transfer is refused on observed relayed paths as a conservative metadata/policy choice pending a dedicated relay-safe file-key/transport design, not because the relay can read the signed offer.
- AutoNAT/DCUtR are best-effort status/hole-punch attempts; ping is liveness only; identify hides listen addresses and bounds protocol/agent strings. None proves a contact's identity or a universal network path.
- The fourth bounded protocol, `/p2p-messenger/control/1`, reuses the opaque 1 MiB frame codec. The controller drains control/discovery/relay/NAT/identify queues to update `NetworkPrivacyStatus`, but promotes nothing to a contact, trust, capability, presence, receipt, or delivery state.
- `NetworkPrivacyStatus` separates configured flags/counts from counters/strings changed only by real libp2p events. GUI rows state limitations and do not claim anonymity, unlinkability, Tor/I2P support, universal NAT traversal, or file transfer over relays.
- Q follow-up: relay-only clients have no direct TCP listener and only configured circuit destinations are dialed; a real local relay test proves circuit listeners and relayed alice/bob connectivity. MLS application plaintext is padded to fixed buckets before encryption and strict padding validation fails closed. `TorRequired` selects a SOCKS5-only transport with no direct listener/fallback and forwards destination domains to the proxy; GUI status says configured (policy only; proxy identity and reachability not established). Proxy identity, real Tor behavior, DNS/IPv6 leak behavior, timing/direction/volume and coarse outer length hiding, metadata confidentiality, unlinkability, and anonymity are not claimed; the epoch-bound route tag remains linkable within its epoch. Q3 v3 metadata reduction and Q4 bounded wire-level deniability are complete locally/uncommitted (Q4 is not ephemeral delegated keys): v3 wire bytes carry no third-party-verifiable long-term application signature/proof, but current group members with MLS state can still attribute messages and outside observers/past members without epoch state cannot turn wire bytes into transferable authorship proof. Full deniability/post-quantum resistance is not claimed.
- ADR-0012 records the accepted decisions and non-claims. Two-machine LAN/NAT/relay and real proxy/Tor verification remain external tests.
