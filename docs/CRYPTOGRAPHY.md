# Cryptography Design

Status: historical design baseline with local identity, local key protection, and Noise transport implemented and tested in Milestones 1–4; initial MLS messaging in Milestone 5; network resilience in Milestone 6; encrypted chunked file transfer and ciphertext-only quarantine in Milestone 7; narrow validation, scanner input, policy/approval-gated release, an encrypted attachment store, a native-only OS save flow, and explicit deletion policies in Milestone 8; multi-member Add/Remove/Update group management in Milestone 9; parent-group channel policy in Milestone 10 plus P1d derived MLS groups for non-default channel text; optional, off-by-default discovery, relay, NAT, identify, and opaque transport-control plumbing in Milestone 13. M13 added no new cryptographic primitive. Current production application messages use the Q3 `P2P3` v3 envelope and Q4 bounded wire-level deniability (implemented locally/uncommitted), setup uses signed PQ v5 over `/p2p-messenger/mls-setup/2`, file frames use signed PQ v3, and the pinned MLS suite is `MLS_192_MLKEM768_AES256GCM_SHA384_MLDSA65` (`0x0051`); these supersede older classical-only, hybrid-Ed25519 `0x004F`, and signed-envelope descriptions below. PQ layers cover MLS KEM/signatures, setup/file signatures, mandatory ML-DSA-65 connection admission with bounded pre-admission observation gating, and direct QUIC X25519MLKEM768 key exchange; TLS/libp2p PeerId authentication and TCP Noise remain classical, so full post-quantum protection is not claimed. Encrypted channel-group persistence/restore, admin role delegation, complete channel ACLs for parent policy/default traffic, general format/MIME parsing, backup/restore, transport-level cancellation of an already queued worker request, a configured independent malware scanner, strong anonymity, full deniability, metadata confidentiality, full post-quantum protection (classical PeerId/TLS authentication remains), universal NAT traversal, and a dedicated relay-safe file-key/transport design for enabling file transfer over relays remain design targets or non-claims. `TorRequired` is configured policy only; proxy identity, reachability, and real Tor behaviour are unverified.

## 2. Local identity

- `libp2p::identity::Keypair::generate_ed25519()` using the OS CSPRNG. No MAC, IP, hostname, serial, or user name as input.
- `PeerId::from(keypair.public())` is the public identifier.
- **Fingerprint**: canonical encoding of the Ed25519 public key, SHA-256, lowercase base32 in 8-character groups, prefixed `P2PMSGR-ED25519-`. Example format (not a real key): `P2PMSGR-ED25519-AB3D 9F02 ...`. Verification compares the full fingerprint; the short prefix is only a convenience and is never sufficient.
- **QR payload**: versioned URI `p2pmsgr://contact/v1/<peerid>?pk=<base64url-public-key>` with an optional display name. It contains no private material and no central URL.
- Contact verification is an explicit user action after comparing fingerprints through an independent channel (voice, in person, another trusted channel). Until then the contact is marked `Unverified`.

### PQ identity (v2 bundles)

- The transport PeerId remains Ed25519/libp2p and is authenticated classically by Noise or TLS. The v2 encrypted identity bundle adds independent ML-DSA-65 seeds for root, device, Mls, Application, and File in `PqSeeds`, plus a self-contained `PqIdentityProof` (~26 KiB) that binds those PQ public keys to the classical transport PeerId and a validity window.
- Classical Ed25519 root/device/transport/Mls/Application/File role keys and the classical proof remain in parallel for transport and legacy compatibility; they are not removed by the PQ layer. A legacy v1 bundle imported without a v2 export generates fresh PQ seeds and a fresh proof rather than reusing or asserting prior PQ material.
- ML-DSA-65 signing uses the pinned `ml-dsa =0.1.2` library with `alloc`; encoded public keys are 1952 bytes and signatures 3309 bytes. No application-defined primitive is introduced.

### Mandatory PQ connection admission

- Every accepted libp2p connection must complete `/p2p-messenger/pq-auth/1` before application request/response events are delivered. `PQA1` version-1 requests carry a fresh 32-byte nonce, the self-contained PQ proof, and a 3309-byte ML-DSA-65 `Application`-role signature over domain `p2p-messenger/pq-auth/challenge/v1`, phase, role code, initiator PeerId, responder PeerId, and nonce. Acks reuse the exact nonce and are sent only after verification.
- Receive verification of the peer's request gates inbound application events; mutual request/ack completion gates `ConnectionState::Connected` and outbound application sends. `max_connections_per_peer == 1` is required so admission state is unambiguous, and the request-response behaviour allows two concurrent streams to avoid deadlock.
- This reuses the existing library-backed PQ identity proof and signature path; it adds no custom primitive and does not replace the classical transport identity. The proof is self-signed and bound to the classical PeerId, so a quantum attacker who forges the transport PeerId could mint a fresh proof bound to it. Optional identify, ping, and relay reservation/circuit bootstrap bytes may still be exchanged before admission; peer-scoped application-visible observations are buffered until that peer completes admission (64-entry cap), while local listener/startup, mDNS, and AutoNAT facts remain direct/advisory.

### Implemented in Milestone 2 (`crates/identity`)

- Fingerprint input is the **raw 32-byte Ed25519 public key**, not protobuf framing. SHA-256 produces 32 bytes; unpadded base32 is 52 characters, rendered as six 8-character groups plus a final 4-character group. Parsing accepts spaces/hyphens but returns the canonical grouped string, and rejects bad prefixes, lengths, non-base32 characters, and uppercase input.
- Contact URI `pk` is base64url-no-pad of the **protobuf-encoded** libp2p public key, so a receiver can reconstruct the exact key and verify it derives the claimed PeerId. A mismatched PeerId is rejected before the contact is accepted.
- Encrypted identity export format: magic `P2PMSGR-IDENTITY-EXP`, version byte, KDF id byte (`1` = Argon2id), little-endian m/t/p costs, 16-byte salt, 24-byte nonce, then XChaCha20-Poly1305 ciphertext with a 16-byte tag. The whole header plus app name and `p2p-messenger/identity-export/v1` is passed as AAD, so parameter or purpose tampering fails authentication. Import bounds m/t/p to 8–512 MiB / 1–10 / 1–8 to avoid hostile-allocation denial of service.

### Device scope

Milestone 2 identities are **device-specific**. An encrypted export can be imported on another device, but that intentionally moves/copies the same private key. True multi-device identities (separate device keys linked to a common long-term identity) are **not** supported in the initial release and must not be advertised as such. Reusing one identity on two devices simultaneously breaks contact assumptions and is documented as unsupported.

## 3. Password and key hierarchy

- On first launch: username, password, local identity. Username is not an account name; it is a local label.
- Salt: 16 random bytes. Argon2id parameters stored alongside the wrapped key: memory 65536 KiB (64 MiB), iterations 3, parallelism 1, output 32 bytes. Parameters are versioned so they can be raised later; existing envelopes retain their original parameters.
- Master key: 32 random bytes, independent of the password.
- Wrapping: XChaCha20-Poly1305 with random 24-byte nonce; AAD binds application name, envelope version, profile UUID, and purpose string `master-key-wrap`.
- Subkeys: HKDF-SHA256(master key, salt = per-purpose random 16-byte salt stored in config, info = `p2p-messenger/v1/<purpose>`). Purposes: `storage/db`, `storage/identity`, `storage/attachments`, `storage/search-index`, `storage/backup`.
- Password change: generate new salt, derive new KEK, re-wrap the same master key. Data keys do not change; no bulk re-encryption.
- Password loss: no recovery without the encrypted backup/recovery key. We will not display language implying otherwise.

Rationale for 64 MiB / t=3 / p=1: meaningful offline guessing cost on commodity hardware while remaining usable on typical desktops; parameters are configurable and recorded in the envelope. This is a baseline, not a claim of resistance to a well-funded attacker.

## 4. Conversation encryption (all conversations)

**Decision: every conversation is an MLS group.** A 1:1 conversation is a 2-member MLS group. This avoids maintaining two encryption implementations.

- Ciphersuite: the pinned `MLS_192_MLKEM768_AES256GCM_SHA384_MLDSA65` (`0x0051`), enabled by the pinned OpenMLS draft feature on `openmls_rust_crypto`/`openmls_traits`. `0x004F` is the previous hybrid-Ed25519 suite and historical; `0x004D` X-Wing is declared but unsupported by the provider and is rejected. MLS leaf signatures and the `Signer` use ML-DSA-65 with certified ML-DSA-65 `Mls` role keys. The libp2p transport still authenticates PeerIds classically (Noise on TCP, TLS on QUIC), so PQ MLS protection is not full post-quantum protection, and no custom primitive is used.
- Credential: OpenMLS `BasicCredential` contains the raw libp2p `PeerId` bytes. The MLS leaf signature key is the certified 1952-byte ML-DSA-65 public key from the v2 vault bundle. Production v3 outer envelopes carry no long-term application signature or identity proof; they are authenticated by a group-keyed exporter MAC and MLS group state. KeyPackage acceptance validates the OpenMLS ML-DSA-65 signature, requires the credential to equal the expected PeerId, requires the expected transport public key to derive that PeerId, and requires the leaf signature key to equal the certified ML-DSA-65 `Mls` key.
- MLS gives: forward secrecy, post-compromise security after commits/updates, group authentication, membership change semantics, epoch separation, and built-in replay protections. M9 implements signed Add/Remove/self-Update commits; removed members remain on the excluded epoch and cannot decrypt later group traffic. Durable MLS state restoration remains a target.
- Application messages carry typed content: text, reply, receipt, pin, policy update, file descriptor, channel metadata. Text, receipts, and bounded `CHN1` channel text/policy bodies are exercised by current tests; the other reserved kinds are not implemented.
- Production v3 outer envelope (`EnvelopeV3`): `V3_MAGIC` `P2P3`, version `3`, a 32-byte route tag (`SHA-256(domain separator || group ID || epoch)`), a fresh random nonce, a `u32` wrapped-body length, the wrapped MLS ciphertext, and a 32-byte HMAC-SHA256 tag. It has no sender, conversation ID, epoch, message ID, sequence, timestamp, kind, certificate proof, role key, or long-term signature in clear. The `V3InnerFrame` (`V3_INNER_MAGIC` `P2I1`/version, conversation ID, message ID, sender `PeerId`, sequence, `created_at`, kind, body) is inside MLS plaintext. The MLS ciphertext is additionally AEAD-wrapped with XChaCha20-Poly1305 under a purpose-separated exporter key, while the outer HMAC uses a separate purpose-separated exporter key; this is library-backed composition, not a custom primitive. The recipient resolves one local group by route tag (zero or ambiguous matches fail closed, wrong tag is `BadRouteTag`), verifies the exporter MAC, unwraps and MLS-decrypts the body, then binds the inner sender to the MLS leaf credential. The legacy signed-v2 envelope is retained only for compatibility/test; production rejects v1/v2 application envelopes.
- Timestamps are untrusted hints recovered from the inner frame. Ordering uses sender sequence number within an epoch, with epoch boundaries from MLS.
- Q3 v3 metadata reduction and Q4 bounded wire-level deniability are implemented locally/uncommitted. v3 wire bytes have no third-party-verifiable long-term application authorship proof; recipients and current group members with MLS state can still attribute a message. A relay or proxy still sees IP, timing, direction, volume, coarse length, and route-tag linkability within an epoch. This is bounded deniability, not full deniability, anonymity, or metadata confidentiality.
- Implemented in `crates/groups`: group creation with the conversation ID as `GroupId`, KeyPackage generation with retained in-memory provider, Add + Welcome join, encrypted compose/receive, encrypted receipts, rejection of re-signed tampered ciphertext or foreign sender/credential mismatch, and M9 `add_member_parts`/`remove_member`/`self_update_commit`/`process_commit` with operation and target binding.
- M9 group policy is application-level: the creator is the admin, and only that identity may start Add/Remove/Update. Commits are signed at the PQ setup v5 `MLS1` frame layer and checked against the authenticated sender and declared operation before merging. A joiner receives the new epoch through the Welcome, not by applying the Add commit.
- M10 channels are `CHN1` plaintext bodies encrypted by the same MLS application path. The production v3 group-keyed outer MAC plus MLS sender binding authenticate the writer to a recipient; `channel_id` is inside the authenticated application body, not a new outer field. Channel membership is local policy, not a separate key boundary.
- Not implemented: admin role delegation, complete channel ACLs for parent policy/default traffic, external commits, setup KeyPackage/Welcome restoration, decrypted-message restoration, and automated policy distribution. Non-default text uses P1d derived MLS groups, and P1e restores ready groups from authenticated encrypted records; incomplete setup groups fail startup rather than revive a partial boundary. With a vault session, joined MLS state, ready channel groups, bounded pending operations, receipts, and queued ciphertext restore through authenticated encrypted records; otherwise in-memory state is lost on restart. No MLS state is written in plaintext.

## 5. File encryption (Milestones 7 and 8 implemented)

A file transfer is **not** an MLS `MessageKind::File` and the transfer itself is not stored in an attachment table. It uses the separate `/p2p-messenger/file/1` protocol over the same transport-authenticated connection, with application-level ML-DSA-65 signatures on every v3 frame: a self-contained `PqIdentityProof` and a 3309-byte File-role signature. Legacy v2 Ed25519 frames decode/verify for adversarial tests only; production paths require v3. After policy-gated release, the desktop application may copy the in-memory plaintext into the encrypted attachment store described below. ADR-0007 records the format and status decisions.

- **Transfer key**: a fresh random 32-byte key is generated for each transfer, held in a `Zeroizing` buffer, carried only inside the signed `Offer`, and never persisted. The content key is protected by the authenticated transport (Noise on TCP/relay/SOCKS5 streams, QUIC TLS on QUIC paths): with pinned `libp2p 0.57.1` the relay client transport uses a Noise upgrade over the selected transport, so a relay forwards opaque bytes and cannot read the offer or the content key. It can still observe PeerIds, IPs, timing, and sizes. File transfer is conservatively disabled on observed relayed paths pending a dedicated relay-safe file-key/transport design; this is a metadata/policy choice, not a claim that the relay sees the key.
- **Chunk AEAD**: `XChaCha20-Poly1305` from the already validated `chacha20poly1305 0.11.0`. Each chunk of at most 256 KiB uses its own random nonce and AAD `p2pmsgr-file-chunk-v1 || transfer_id || index || chunk_count || exact_plaintext_length`. The AAD binds ordering, total count, and length; out-of-order, duplicate, truncated, or tampered chunks fail closed. Files are limited to 64 MiB and 256 chunks.
- **Integrity**: SHA-256 per chunk and over the full plaintext, plus a domain-separated manifest commitment over transfer ID, chunk count, all chunk hashes, and the full hash. The commitment hash is signed in the offer, so the later signed manifest cannot be substituted. Verification decrypts ciphertext chunk by chunk in bounded zeroizing buffers, compares every hash, and checks the full digest. `IntegrityVerified` means byte agreement only.
- **At rest in M7**: the receiver writes only AEAD ciphertext into a `0700` quarantine directory (`0600` chunk files on Unix), plus a hash-only manifest record. No plaintext or content key is written to quarantine. Restricted permissions are enforced on Unix; equivalent ACL work remains a platform target.
- **M8 validation/scan/release boundary**: `SecurityConfig::scan` first performs dependency-free structural checks for TXT (UTF-8 without disallowed control bytes), PNG (signature/chunk/CRC/IHDR/IEND), and GIF (header/block/trailer). A claimed-format mismatch returns `UnsupportedFormat` before scanning. An application-supplied `FileScanner` then receives a bounded in-memory plaintext buffer and returns one exact category. Only `SecurityConfig::scan` can create a `ScanOutcome`; a clean category and validated format cannot be fabricated by integrity checking or by another application caller. Policy release requires that outcome, a validated format, a safe base name, non-empty bounded size/chunk count, an explicit extension allowlist, and explicit per-file `Approved` status. `ReleasedFile` is zeroizing memory; the desktop app copies it into the encrypted store, and the native OS save dialog writes plaintext only to a user-chosen path. The default app config has no scanner and no allowed extensions. `cancel_file` is terminal for release of an integrity-verified transfer and keeps verified ciphertext in quarantine; an active transfer instead has an inactivity deadline and `abort_file`, which zeroizes its fresh content key and removes incomplete ciphertext.
- **Still not implemented**: general format/MIME parsing, media previews, a configured real scanner, backup/restore, and transport-level cancellation of an already queued worker request. Structural validation is not malware detection; a "clean" or "safe" file status must not be shown without a real independent scanner result.

The `storage/attachments` subkey is used by M8. `Session::store_attachment` creates a random 16-byte ID and a random per-file key; the ID is HMAC blind-indexed with the profile ID and used as both the primary key and blob filename. The per-file key is wrapped under `storage/attachments` with profile/blind-index AAD, and the blob is XChaCha20-Poly1305 ciphertext at `attachments/<blind-index-hex>.ct`. Name, size, SHA-256 digest, and narrow uppercase format label are encrypted under that per-file key. Reads reject symlinks, check the bound and stored size, recheck the digest, and return a zeroizing buffer. Deletion is explicit; `change_password` rewraps only the vault master key. Attachments are single bounded ciphertext records up to 64 MiB, so there is no separate attachment chunk-AAD scheme.

## 6. Metadata and privacy hardening (M13, implemented)

M13 itself introduced no new cipher, KDF, signature scheme, or key hierarchy. It enables optional libp2p behaviours that are off/empty by default and adds a fourth bounded request-response protocol, `/p2p-messenger/control/1`, that reuses the existing 1 MiB opaque frame codec. Later Q3/Q4 v3 composition reuses library HMAC-SHA256, SHA-256, XChaCha20-Poly1305, and MLS exporter keys; the PQ work adds library ML-DSA-65 identity/setup/file signatures and QUIC's X25519MLKEM768 KEX under pinned libp2p-tls, but no custom primitive. The v3 application wire still has no long-term application signature; setup and file frames are signed separately.

- The control protocol is deliberately not signed or MLS-encrypted at the application layer. It has no cryptographic meaning: it cannot authenticate a human, grant a capability, acknowledge a message, or prove presence. The controller drains its events and records no application state from them.
- Identify, when explicitly enabled, hides listen addresses, pushes no address updates, uses a long interval, and bounds protocol/agent strings before they enter events or diagnostics. It reveals a bounded protocol/agent description to connected peers and does not authenticate the person behind the PeerId.
- mDNS/Kademlia discovery and relay/NAT observations are advisory metadata. Kademlia needs user-supplied direct bootstrap addresses; `/p2p-circuit` and peerless addresses are rejected. Discovered candidates are never auto-dialed or promoted to trusted/verified contacts.
- Relay operators (and a configured SOCKS5 proxy) see PeerIds, IP addresses, timing, direction, volume, and coarse lengths, and can deny service; v3 route tags remain linkable within an epoch. The Noise upgrade means relays forward opaque bytes and do not receive private keys, message keys, or file keys/application plaintext. Relayed connections are capped/counted from real transport observations. The signed PQ file offer carries the fresh content key inside transport-protected bytes; file transfer is nonetheless refused on observed relayed paths as a conservative metadata/policy choice until a dedicated relay-safe file-key/transport design exists. Relay reservation/circuit counters describe events observed since startup, not live state.
- AutoNAT and DCUtR are best-effort observations/hole-punch attempts; ping is liveness only. `NetworkPrivacyStatus` separates local configuration from fact-derived counters and strings, so the GUI cannot present a configured option as an observed capability.
- There is no strong anonymity, Tor/I2P/mixnet, metadata confidentiality, unlinkability, full deniability, universal NAT traversal, or cryptographic channel ACL added by M13 or the v3 wire. `TorRequired` with a SOCKS5 proxy is configured route policy only; proxy identity, reachability, and real Tor behaviour are unverified and must not be reported as an observed anonymity property.

## 7. Non-goals / residual risks

- The initial stable release had no quantum-resistant conversation cipher. The current pinned build enables `MLS_192_MLKEM768_AES256GCM_SHA384_MLDSA65` (`0x0051`) via the pinned draft feature, with ML-DSA-65 leaf signatures and certified ML-DSA-65 `Mls` role keys; setup v5 and file v3 frames carry ML-DSA-65 signatures, `/p2p-messenger/pq-auth/1` requires ML-DSA-65 connection admission before application events, and direct QUIC negotiates X25519MLKEM768 through pinned libp2p-tls/rustls `prefer-post-quantum`. Suite `0x004F` (previous hybrid-Ed25519) is historical; `0x004D` X-Wing is declared but unsupported by the pinned provider. TLS/libp2p PeerId authentication and TCP Noise remain classical, so full post-quantum protection/quantum resistance is not claimed, and no custom crypto is used. Literal TLS/Noise PeerId replacement would need a vendored/forked transport with the pinned dependencies.
- No anonymity network integration. Peer IPs are visible to direct peers, user-chosen relays, and a configured SOCKS5 proxy; optional discovery reveals queries/candidates to user-chosen peers. Tor/I2P/mixnet support, metadata confidentiality, and unlinkability would be separate designs. M13 relay/NAT/identify features do not provide them. v3 gives only bounded wire-level deniability: no third-party-verifiable long-term application authorship proof in the wire bytes, but recipients/current group members with MLS state can still attribute messages, and route tags remain linkable within an epoch. `TorRequired` is configured policy only; proxy identity, reachability, and Tor behaviour are unverified.
- MLS group state was memory-only in the numbered milestones; Phase 4 can now restore joined group state from the encrypted vault when a session is attached. A compromised device can still read history available to that member, setup KeyPackages/Welcomes and decrypted text do not survive restart, and forward secrecy limits past traffic rather than data still stored locally.
- File integrity is not malware safety. M8 adds narrow structural validation, an application-supplied scanner interface, release policy, explicit approval, an encrypted attachment store, and a user-chosen native OS save path, but no scanner is configured in the desktop app and no general file-type parser exists. The attachment store does not make an unscanned file safe; `IntegrityVerified` and structural validation must never be rendered as "clean".
- Application-level admin permissions and channel memberships are policy enforced by clients, not a cryptographic role or key system. The creator-as-admin M9 design and its limits are recorded in ADR-0008; the M10 channel design and its non-ACL limitation are recorded in ADR-0009. All MLS group members hold group keys, so a restricted channel is not a confidentiality boundary against another group member.
