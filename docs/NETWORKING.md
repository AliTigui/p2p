# Networking Design

Status: **Milestones 4–10 and 13 complete**: zero-infrastructure direct connect, MLS payload encryption, signed MLS setup/group control, the `p2p-chat` controller, the GUI send/receive path, the in-memory offline queue with reconnect retry, bounded redial/backoff, duplicate-dial rejection, connection admission limits, aggregate per-peer and per-protocol request/byte budgets, admin-only multi-member group management, group-wide delivery receipts, logical `CHN1` channels, the separate encrypted file protocol with ciphertext-only quarantine and an approval gate, plus optional M13 discovery, relay, NAT, identify, and control plumbing. A post-M13 local schema-v4 control-frame digest log with a vault anchor preserves only already authenticated setup/group-control decisions across restart; it changes no transport or wire format and restores no MLS state. M13 capabilities are **off/empty by default** and are not required for any core function. The local Q follow-up adds explicit relay-only routing, a configured SOCKS5-only outbound transport, fixed-bucket MLS application padding, and Q3/Q4 v3 wire work that is complete locally/uncommitted. Production application messages are P2P3 `EnvelopeV3` with an epoch-bound route tag and MLS-protected inner metadata; setup is signed PQ v5 over `/p2p-messenger/mls-setup/2` with only suite `0x0051` accepted, and file frames are signed PQ v3 on `/p2p-messenger/file/1`. Legacy setup v4 and file v2 codecs decode/verify for adversarial tests only; production paths require PQ. Direct transport is TCP + Noise + Yamux or QUIC with X25519MLKEM768 hybrid key exchange, but TLS/libp2p PeerId authentication and TCP Noise remain classical. Mandatory `/p2p-messenger/pq-auth/1` ML-DSA-65 admission runs before application events and peer-scoped optional observations, but does not make classical PeerId authentication quantum-resistant; this is not full post-quantum protection. Q4 is bounded wire-level deniability, not delegated keys, and no full deniability or anonymity is claimed. Two-machine LAN/NAT/relay/real-proxy verification, strong anonymity, universal NAT traversal, a real scanner, general MIME parsing, backup/restore, and transport-level cancellation of an already queued worker request remain targets. See `PROJECT_STATUS.md` for actual commands and results.

## 1. Goal and constraint

The application must work with **zero infrastructure owned or operated by the project**. User installations are equal peers. Discovery and relay are optional capabilities provided by users' own installations, never mandatory services. No developer-operated bootstrap addresses, relays, or discovery peers are compiled into the binary.

The networking foundation is `libp2p =0.57.1`. Transport features are `ed25519`, `macros`, `tcp`, `noise`, `yamux`, `quic`, and `tokio`. M13 explicitly adds `autonat`, `dcutr`, `identify`, `kad`, `mdns`, `ping`, and `relay` features; their behaviours are created only when the local user enables them. Four explicit protocols use `libp2p-request-response =0.30.0`, the version paired with libp2p 0.57. The 0.57 line was unlocked by moving the native GUI to egui/eframe 0.35, which removed the `js-sys` graph conflict with `libp2p-swarm 0.48.0`; the full rationale is in `docs/DEPENDENCIES.md`. Q5 adds `tokio-socks = =0.5.3` and `tokio-util`'s `compat` feature for a SOCKS5-only configured transport; it is not a libp2p feature and does not modify the default direct transport. The PQ work adds pinned `ml-dsa =0.1.2` (`alloc`) for setup/file/identity/connection-admission signatures, `getrandom.workspace = true` in `p2p-network` for fresh admission nonces, and enables the libp2p `quic` feature; its transitive `libp2p-tls 0.7.0` uses rustls `prefer-post-quantum` and negotiates X25519MLKEM768. Q3 adds `hmac` + `sha2` in `p2p-messaging` and `p2p-crypto` in `p2p-groups`; the pinned OpenMLS draft feature brings PQ transitive crates into the lockfiles. `plaintext`, `pnet`, `floodsub`, DNS, UPnP, and a facade `request-response` feature remain excluded.

## 2. Connection modes

### Mode A — Direct connection (implemented, default)
- The user enters a multiaddr such as `/ip4/203.0.113.10/tcp/4001/p2p/12D3Koo...`; the `/p2p/<peer-id>` suffix is required and `/p2p-circuit` is rejected for user-supplied direct addresses.
- `Network::parse_address` validates the address and extracts the expected PeerId before dialing. The first dial comes only from an explicit user action in the GUI or API; bounded automatic redial reuses that saved address after an observed disconnect or attributed dial failure. A user disconnect suppresses further redial until a fresh explicit dial.
- The direct transport is `OrTransport` of TCP + Noise + Yamux and QUIC under `PerIpPendingTransport`. TCP Noise authenticates that the remote controls the private key for the expected PeerId; QUIC uses pinned libp2p-tls 0.7.0/rustls with `prefer-post-quantum` and X25519MLKEM768 hybrid key exchange, while its TLS/libp2p PeerId authentication remains classical. The local key is imported from the encrypted vault via the stable protobuf Keypair encoding, so the network PeerId matches the vault transport identity. Application-layer ML-DSA-65 setup/file proofs bind role keys to that PeerId, and every connection must complete `/p2p-messenger/pq-auth/1` before application events or `Connected` state; this is not full post-quantum protection because the admission proof is bound to a classically authenticated PeerId.
- The default listen address is `/ip4/0.0.0.0/tcp/0`, with a corresponding QUIC listener; loopback with an ephemeral port is used in tests. Direct TCP/QUIC listeners are not opened in `TransportPrivacyMode::TorRequired` or `DialPolicy::RelayOnly`.
- No bootstrap, DHT, relay, account service, developer server, identify, or ping is involved by default. This is the acceptance test for "no centralized server", and it passes with two isolated instances on loopback.
- Identify is off by default. When explicitly enabled, it hides listen addresses and bounds protocol/agent strings, but a connected PeerId still does not prove the person is the intended contact. Fingerprints are verified out of band.

### Mode B — Local network discovery (optional, implemented; two-machine test pending)
- `enable_mdns` creates a bounded libp2p mDNS behaviour. Discovered peer/address pairs become advisory candidates reported through `DiscoveryEvent`/`NetworkPrivacyStatus`.
- mDNS is never defaulted. Discovered peers are not auto-dialed, saved as contacts, trusted, or treated as fingerprint-verified. Users still supply the address and verify the fingerprint out of band.
- mDNS is usually limited to a local broadcast domain and may be disabled by OS or network policy. Local reachability is not guaranteed.

### Mode C — Distributed discovery (optional, implemented; two-machine test pending)
- `enable_kad` creates a Kademlia behaviour with an in-memory store, caching disabled, and no periodic publication/bootstrap refresh. It requires at least one **user-supplied** direct bootstrap address ending in `/p2p/<peer-id>`; no default server exists.
- Kademlia events update advisory route/candidate counters. They never auto-dial a discovered peer or promote it to a contact or verified identity.
- No rendezvous service is configured. A user-operated rendezvous alternative would need separate design and dependency review.

### Mode D — Peer-operated relays and relay-only routing (optional, implemented; two-machine test pending)
- `RelayMode::Client` requires user-supplied direct relay addresses ending in `/p2p/<peer-id>`; `/p2p-circuit` bootstrap/relay configuration is rejected. The worker listens on circuit addresses built from those user inputs; reservations and circuits are reported from real libp2p relay events.
- `RelayMode::Server` creates a bounded relay service with configured circuit, per-peer, byte, reservation, and circuit-source limits. Explicit server mode enables the libp2p HOP status, and concrete non-wildcard `NewListenAddr` values are advertised as external addresses; wildcard listens are not advertised.
- Q1's `DialPolicy::RelayOnly` requires relay-client mode and rejects direct application dials and direct TCP/QUIC listeners (relay reservation dials still use the configured transport). `Network::dial_relayed` accepts only a circuit address built from a configured relay and ending in the destination PeerId. Circuit listener state is emitted only after a reservation is accepted. Non-relayed inbound connections from non-relay peers are closed, and application traffic is allowed only on an observed relayed path. A local integration test uses a real relay server to prove circuit-only listeners, reservations, a relay-observed circuit, and relayed alice/bob connectivity.
- Relayed connections are separately capped (`max_relayed_connections`, default 4) and counted from observed `is_relayed()` connections. A relayed connection does not imply trust, a reservation, a verified contact, or message delivery.
- With pinned `libp2p 0.57.1`, the relay client transport is upgraded with the same Noise security upgrade as direct TCP. A relay forwards opaque Noise bytes between endpoints: it can observe PeerIds, IPs, timing, and sizes and can deny service, but it cannot read application plaintext, message keys, or the file content key.
- **File transfer over a relay is disabled.** This is a conservative metadata/policy choice, not a claim that a relay sees the framed offer or file key. `Network::send_file` and inbound file requests emit `FileEvent::Failed` with `file transfer over a relay is disabled by policy` when a peer has an observed relayed connection. A dedicated relay-safe file-key/transport design is required before this restriction is changed.
- `relay_reservations` and `relay_circuits` count events observed since worker startup, not currently held reservations or circuits. `relayed_connections` is the latest live count reported by a transport event. `identified_peers` counts identify events observed since startup, not currently connected peers. The GUI labels these facts explicitly. Peer-scoped reservation, circuit, relayed-connection, identify, Kademlia, and DCUtR counters now advance only when the observation is released after PQ admission; mDNS, local listener/startup failures, and AutoNAT status remain direct/advisory.

### Mode E — NAT status, identify, and control observations (optional, implemented)
- `enable_autonat` runs best-effort AutoNAT status probing; `enable_dcutr` attempts hole punching when a relayed path exists. `NatEvent` reports static status categories and hole-punch outcomes. DCUtR hole-punch observations are peer-scoped and released only after PQ admission; AutoNAT status is advisory without full admission context. Neither feature guarantees symmetric-NAT/CGNAT traversal.
- `enable_identify` enables libp2p identify with hidden listen addresses, no pushed address updates, an hourly interval, and bounded protocol/agent strings. Peer-provided addresses are not retained in `IdentifyEvent`, and identify results/errors are peer-scoped observations released only after PQ admission.
- `enable_ping` enables low-frequency (60 s) liveness pings; ping events are not application health or delivery claims and have no peer-admission observation.
- `/p2p-messenger/control/1` carries bounded opaque control frames. The controller drains them but derives no capability, presence, receipt, delivery, trust, or safety state. It is a transport observation only.

### Mode F — SOCKS5-only outbound route (optional, implemented; route policy only)
- `TransportPrivacyMode::TorRequired` selects `Socks5OnlyTransport`. A user-supplied `socks5_proxy` must be an IP literal and port; hostnames are rejected. DNS names in `/dns4` or `/dns6` destinations are handed to the proxy as domain CONNECT targets, so this app performs no local destination lookup. `/dnsaddr`, UDP, `/p2p-circuit`, and incomplete targets fail before a dial future is created.
- Proxy mode has no direct listener: `listen_on` always fails, the worker skips the direct TCP/QUIC listeners, and no direct fallback transport is built. Noise/Yamux upgrades run over the SOCKS5 stream; QUIC is not used in this mode. Configuration rejects a missing proxy, a proxy without `TorRequired`, and mDNS/AutoNAT/DCUtR combined with the route.
- A fake-proxy test observes the SOCKS5 greeting and CONNECT request and proves `example.onion` reaches the proxy as a domain. This is a local route proof only; proxy identity, reachability, real Tor behavior, DNS/IPv6 leaks, packet-capture fallback absence, and anonymity are unverified.
- The advanced GUI labels this mode “SOCKS5/Tor required” and the status row “Configured (proxy identity and reachability not verified)”. It never displays a verified anonymity state.

## 3. Protocol stack

Implemented:

```
P2P3 EnvelopeV3: `V3_MAGIC`/version, epoch-bound route tag, random nonce, wrapped MLS body, HMAC-SHA256 tag
    ↑ stable sender/conversation/epoch/message ID/sequence/timestamp/kind/receipt metadata is in the MLS-protected inner frame
/p2p-messenger/pq-auth/1 (mandatory ML-DSA-65 connection admission; 2 streams; max_connections_per_peer == 1)
    ↑ both PeerIds, phase, Application role, fresh 32-byte nonce, self-contained PQ proof; gates application events, Connected state, and peer-scoped observations
/p2p-messenger/message/1 (bounded request-response, opaque transport bytes)
    ↑ multistream-select negotiation, Full inbound/outbound, 8 streams
signed PQ setup v5 with a self-contained PqIdentityProof (~26 KiB), a 3309-byte ML-DSA-65 Application-role signature, `ciphersuite_id` at bytes 6..8 and a 16-byte transaction ID at bytes 8..24; only `0x0051` accepted: KeyPackageRequest/Response, Welcome, WelcomeAck, GroupJoinRequest/Response, GroupWelcome, GroupCommit/Ack, GroupWelcomeAck
    ↑ p2p-chat verifies signature, authenticated peer, ciphersuite, and transaction binding before MLS state changes; legacy v4 frames are adversarial-test only
/p2p-messenger/mls-setup/2 (bounded request-response, opaque transport bytes)
    ↑ multistream-select negotiation, Full inbound/outbound, 4 streams
signed PQ `FILE` v3 frames: Offer/Accept/Chunk/ChunkAck/Manifest/ManifestAck/Reject, with a self-contained PqIdentityProof and a 3309-byte ML-DSA-65 File-role signature
    ↑ p2p-files verifies signature and authenticated peer, encrypts chunks, checks hashes; legacy v2 frames are adversarial-test only
/p2p-messenger/file/1 (bounded request-response, opaque transport bytes)
    ↑ multistream-select negotiation, Full inbound/outbound, 4 streams
/p2p-messenger/control/1 (bounded request-response, opaque transport bytes; M13)
    ↑ controller drains frames; no application semantics are inferred
TCP: Noise (authenticated encryption, peer identity binding) + Yamux; QUIC: libp2p-tls 0.7.0/rustls with X25519MLKEM768 (TLS PeerId authentication classical)
Yamux multiplexing on TCP/SOCKS5/relay streams; QUIC streams via Quinn
TCP/QUIC direct transport, optional user-configured relay transport, or SOCKS5-only outbound transport
libp2p Swarm (10s connection and request timeout)
    ↑ real Swarm events: listening, dialing, connected, disconnected, relayed, discovery, NAT, identify, failures
ConnectionState, MessageEvent, SetupEvent, FileEvent, ControlEvent, and advisory privacy events projected to the controller/GUI
```

Only these four application protocols exist, plus the mandatory PQ admission protocol. They are separate protocols with separately bounded events; setup, file, and control frames are never treated as chat messages. Unknown protocol names are rejected by multistream-select; application decoders reject v1/v2 application envelopes, setup v1–v3 frames, unknown suites other than `0x0051`, and unknown file versions, with no silent downgrade. Production receive paths additionally require PQ setup v5 and file v3; setup v4 and file v2 remain decodable/verifiable for adversarial tests only. The legacy `/p2p-messenger/mls-setup/1` path is not the production setup route. Concurrent pending sockets are capped before Noise authentication (16 inbound and 16 outbound by default), and direct TCP sockets are capped per source IP by `max_connections_per_ip` (four by default) before any Noise bytes are processed; zero/oversized limits are rejected at configuration time. Established connections are capped globally, per authenticated PeerId, and per observed IP; relayed connections have an additional cap. Configuration requires `max_connections_per_peer == 1`; inbound application events require a verified peer admission request on that connection, while `Connected` state and outbound application sends require both directions to complete. Peer-scoped optional observations are buffered until that peer completes admission (64-entry cap) and dropped if the connection closes first; the underlying relay bootstrap/identify protocol bytes may still occur before admission. Peerless inbound failures are reported as advisory events without replacing cached live connection state. Duplicate pending dials are rejected; inbound application requests are limited by an aggregate sliding per-peer request-count and byte budget with derived per-protocol reservations for message, setup, file, and control traffic before they reach the application decoder. A denied request is not charged to either window, so one saturated protocol cannot consume another protocol's reserved capacity. File transfers are additionally bounded to 64 MiB, 256 KiB chunks, and 256 chunks. Scanner-driven release is an application-layer gate, not a wire-protocol step: it requires structurally validated TXT/PNG/GIF content, a real scanner result, name/size/count/extension policy, and explicit per-file approval before returning plaintext to memory. The post-M13 local control-log/anchor increment is vault-only: it changes no wire format, adds no protocol, and is unrelated to the opaque `/p2p-messenger/control/1` protocol.

## 4. Security controls

### Implemented
- **Transport peer authentication**: the dialed address must contain the expected PeerId; TCP/SOCKS5 Noise (and relay upgrades) authenticate that PeerId classically, while QUIC's libp2p-tls authentication is also classical despite its X25519MLKEM768 hybrid KEX. User-supplied bootstrap/relay addresses must also be direct `/p2p/<peer-id>` addresses and never contain `/p2p-circuit`. Setup/file ML-DSA-65 proofs bind application roles to that PeerId.
- **Mandatory PQ connection admission**: `/p2p-messenger/pq-auth/1` requires both endpoints to sign a domain-separated challenge binding both PeerIds, phase, `Application` role, and a fresh 32-byte nonce with the certified ML-DSA-65 `Application` key. Malformed, wrong-peer, wrong-nonce, substituted-proof, and tampered-signature requests fail closed. Inbound application events require receive verification, while `Connected` and outbound application sends require the local request to be acknowledged. This gate runs over a classically authenticated connection; identify/ping/relay reservation/circuit bootstrap bytes may still be exchanged before it, while peer-scoped observations are buffered until the peer completes admission (64-entry cap). It does not make TLS/Noise PeerId authentication quantum-resistant.
- **Relay-only route policy**: `DialPolicy::RelayOnly` refuses direct dials/listeners, accepts only configured circuit destinations, and gates application traffic on an observed relayed path. It hides the source IP from the destination peer, not from the relay.
- **SOCKS5-only route policy**: proxy mode forwards destination domains to the configured proxy, rejects local-resolution targets, disables direct listeners/fallback, and fails closed on conflicting discovery/NAT flags. It does not verify the proxy, Tor, or anonymity.
- **Coarse MLS length hiding**: Q2 pads MLS application plaintext to fixed buckets before encryption and rejects malformed padding after decryption; no timing, direction, volume, or outer-frame hiding is claimed.
- **V3 outer routing and integrity**: `route tag = SHA-256(domain separator || group ID || epoch)` is a local routing hint only, not a secret, authorship proof, or unlinkability guarantee. Zero or ambiguous routes fail closed. The MAC is an exporter-derived HMAC-SHA256 key separate from the XChaCha20-Poly1305 exporter key that wraps the MLS body.
- **Application message binding**: the P2P3 outer frame has no long-term application signature or clear stable metadata; sender, conversation ID, epoch, message ID, sequence, timestamp, kind, and receipt body are checked in the MLS-protected inner frame after group-authenticated decryption, before replay or delivery state changes.
- **End-to-end payload confidentiality**: `p2p-groups` produces MLS ciphertext for the wrapped body, including receipt bodies, with ML-DSA-65 leaf signatures under the `0x0051` suite; the MLS ciphertext is additionally wrapped under a purpose-separated exporter key. Receipt verification checks the MLS credential, ML-DSA-65 member signature key, group ID, and epoch against the authenticated inner-frame sender.
- **Signed setup binding**: setup v5 over `/p2p-messenger/mls-setup/2` carries a self-contained PqIdentityProof (~26 KiB) and a 3309-byte ML-DSA-65 `Application`-role signature over the frame, including `ciphersuite_id` bytes 6..8 (only `0x0051` accepted) and a random transaction ID at bytes 8..24. `p2p-chat` verifies the frame and certified PQ Application key against the transport-authenticated peer before OpenMLS sees a KeyPackage or Welcome; v1–v3, legacy v4, and unknown suites are rejected. Pending state and acknowledgements are keyed by transaction ID; channel frames additionally require a PQ `verify_channel_scope` check.
- **Signed group control and channel policy**: bounded PQ setup/group-control frames carry Add/Remove/Update with pending acknowledgement state; `CHN1` bodies stay inside MLS application plaintext and are locally gated by admin/member policy. Neither is a cryptographic role or channel-ACL system.
- **Honest connection and message state**: `ConnectionState` comes only from real Swarm events. `SentToPeer` never means delivered; `Joined` requires verified setup completion; `IntegrityVerified` requires a verified signed manifest. `ControlEvent` and privacy observations never claim application state.
- **No mandatory infrastructure**: all bootstrap lists, relay lists, discovery flags, identify/ping, AutoNAT, and DCUtR default to off/empty; no developer-operated service exists.
- **Bounded application frames**: request and response frames are capped at 1 MiB, with empty/oversized lengths rejected before body allocation. Eight concurrent message streams and four setup/file/control streams are allowed, with a 10-second timeout.
- **Bounded optional network surface**: mDNS/Kademlia candidates are advisory; cumulative relay reservation/circuit events observed since startup and the latest live relayed-connection count come from real events released after PQ admission, and relayed connections are separately capped; AutoNAT results are best-effort and DCUtR hole-punch observations are admission-gated; identify strings are bounded, listen addresses hidden, and identify observations admission-gated; the controller drains privacy/control queues without promoting their contents.
- **File transfer isolation**: a transfer starts only with a joined MLS conversation and only one transfer is active per peer. Fresh content keys, bound AEAD AAD, manifest commitments, ciphertext-only quarantine, redacted diagnostics, and a hard refusal on relayed paths keep file verification separate from message delivery.
- **Verified replay boundary**: bounded message-ID cache and strict per-sender sequence high-water marks are applied before application state changes.
- **File policy and storage boundary**: the scanner/policy/approval gate, encrypted attachment store, native-only user-initiated OS save, and explicit deletion policies are implemented at the application layer.

### Designed or partially implemented
- **Identify cross-check**: identify can be enabled and its strings bounded, but the application does not cross-check protocol lists or treat identify as contact verification.
- **Two-machine discovery/NAT/relay verification**: local tests validate configuration, validation, bounded events, and status plumbing; LAN/NAT/relay connectivity between separate machines remains an external test.
- **Strong anonymity and universal NAT traversal**: not implemented. Optional relays, AutoNAT/DCUtR, relay-only routing, and configured SOCKS5 routes do not hide all metadata or guarantee connectivity; Q5 does not verify Tor/proxy identity. Q3 v3 metadata reduction and Q4 bounded wire-level deniability are complete locally/uncommitted, not delegated keys; group members with MLS state can still attribute, and no full deniability, unlinkability, or metadata confidentiality is claimed.
- **File policy limits**: general format/MIME parsing, a configured real scanner, backup/restore, and transport-level cancellation of an already queued worker request are not implemented.
- **MLS features beyond M13**: admin role delegation/changes and external commits are not implemented; P1d's derived text groups do not cover parent policy/default traffic. P1e now restores ready derived groups with authenticated binding checks. ADR-0014 Phase 4 later added encrypted restoration of joined group state, channel policy, bounded pending operations, receipts, and queued ciphertext when a vault session is attached; setup KeyPackages/Welcomes and decrypted text remain memory-only.

## 5. Honest limitations

- Symmetric NAT, CGNAT, strict firewalls, or networks that block inbound connections can still prevent direct connectivity. AutoNAT, DCUtR, and relays are best-effort options, not a guarantee.
- Without a reachable peer and a manually supplied address, two offline-isolated machines cannot communicate. The UI says the network is listening or disconnected based on observed events; it does not invent a connection.
- mDNS is limited to its local broadcast domain and may be disabled by OS/network policy. Kademlia requires user-supplied bootstrap peers; no default overlay exists.
- A connected PeerId, discovery candidate, identify result, relay reservation, or NAT observation is not proof that the person is the intended contact. Fingerprint verification remains explicit and out of band.
- Discovery candidates are never auto-dialed. The user still supplies the peer address and peer ID; no message or file is sent until the user initiates it.
- Relay operators can observe IPs, timing, direction, volume, coarse outer length, and epoch-bound route-tag linkability and can deny service, but the Noise upgrade means they forward opaque bytes rather than application plaintext. Relayed paths are capped and reported, but they are not trusted paths. Relay-only routing changes the destination peer's view, not the relay's view.
- A configured SOCKS5 route is only a proxy route: the proxy operator can observe destination, IP, timing, direction, volume, coarse outer length, and route-tag linkability within an epoch; local tests use a fake proxy, and no real Tor identity, reachability, DNS/IPv6 leak test, or anonymity claim is established.
- File transfer is refused on observed relayed connections as a conservative metadata/policy choice until a dedicated relay-safe file-key/transport design exists; the relay is not assumed to see the file key. Integrity verification alone never means a file is clean or safe.
- Offline queueing is ciphertext-only. Text composed while the peer is disconnected stays `Queued`; the controller retries it only after consuming a real `Connected` event for that peer. With a vault session the queue is encrypted and restored after restart; without one it is per-session and lost on lock. Retry never creates `Delivered` without a verified receipt.
- Without a vault session, MLS group state and decrypted text are memory-only and restart loses the local MLS session. With a session, Phase 4 and P1e restore joined groups, ready derived channel groups, channel policy, bounded pending operations, receipt expectations, and queued ciphertext from authenticated encrypted records; setup KeyPackages/Welcomes and decrypted text remain unavailable after restart. Opaque envelope records and authenticated control-frame digests alone do not restore MLS state and are not a backup.
- Setup v4 and group-control frames have signed transaction IDs, a bounded 512-entry in-memory digest replay cache for exact authenticated replays, and bounded group-commit byte caches. With a cloned vault `Session` attached via `MessengerController::start_with_control_log`, schema v4 additionally records SHA-256 digests of already authenticated frames in a bounded (4,096-record, fail-closed) encrypted chain with a separate AEAD-protected anchor. `KeyPackageRequest` and `GroupJoinRequest` repeats remain idempotent; Welcomes, responses, commits, and all acks are non-repeatable and stay rejected after restart. A duplicate with a different transaction ID cannot overwrite pending state. Request correlation, signed transaction IDs, ownership, membership checks, and terminal-state guards reject late, stale, and unexpected frames. Unlock verifies records, chain, blind indexes, and anchor, detecting database-only rollback and anchor tampering; restoring the entire vault including the anchor is not locally detectable because no external anchor exists. Neither cache is a general replay-proof protocol, and no transport behaviour changes.
- A required member that is offline can leave a group operation pending until it reconnects; the app reports pending state rather than success, and there is no timeout, rollback, or silent partial completion.
- Group `Delivered` requires receipts from every expected member. One disconnected recipient keeps the message at `Queued`/unconfirmed; a vault-backed queue can survive restart, but no restored entry is treated as delivered without a verified receipt.

## 6. Test plan

1. **Implemented and passing**: two instances on one machine with distinct identities and explicit loopback multiaddrs connect with zero bootstrap/DHT/relay, mutually observe the expected PeerIds, and observe disconnect.
2. **Implemented and passing (current v3 wire; historical pre-v3 signed-envelope test retained)**: a P2P3 `EnvelopeV3` carrying a wrapped MLS body is sent over `/p2p-messenger/message/1`, checked through its epoch-bound route tag/MAC and MLS-protected inner frame, decrypted by the recipient, and an explicit MLS-encrypted receipt advances the sender from `SentToPeer` to `Delivered`. A tampered outer frame or inner binding is rejected and leaves the sender at `SentToPeer`.
3. **Implemented and passing (current PQ setup v5; legacy v4 frames adversarial-test only)**: two controllers on explicit loopback connections complete the signed, transaction-bound KeyPackage/Welcome/WelcomeAck exchange over `/p2p-messenger/mls-setup/2`, accept only `0x0051`, reach the same epoch, exchange encrypted text, and reject setup without a connected peer.
4. **Implemented and passing**: text composed while disconnected stays `Queued` through repeated polls, is retried only after an observed reconnect, reaches `SentToPeer` before the recipient is polled, and becomes `Delivered` only after a verified receipt. A raw vault/WAL/SHM scan finds no queued plaintext sentinel.
5. **Implemented and passing**: bounded redial against an unreachable user-supplied address reaches its retry limit without a connected claim; user disconnect suppresses redial until a fresh explicit dial.
6. **Implemented and passing**: a duplicate dial is rejected until the first settles, an extra peer is blocked by a one-connection cap, a second request from one peer is rejected by the aggregate request budget, and control traffic that saturates its own bucket cannot block a later message request.
7. **Implemented and passing**: three controllers on explicit loopback connections complete an admin Add through signed group frames, clear pending state after Welcome/Commit acknowledgements, broadcast text to all current members, and show `Delivered` only after both receipts. Admin Remove advances the epoch and excludes the removed member; self-Update is acknowledged by every member; non-admin operations are denied.
8. **Implemented and passing**: signed PQ file v3 frames cross `/p2p-messenger/file/1` over the authenticated transport; two controllers transfer a multi-chunk file, both sides reach `IntegrityVerified`, scanning stays `Unavailable`, and quarantine bytes contain no plaintext sentinel.
