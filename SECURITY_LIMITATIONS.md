# Security and Privacy Limitations

This document is intentionally conservative. It lists what the implementation does **not** provide. Any claim not supported by source, tests, or an external verification record should be treated as absent.

## 1. Identity limitations

- P2 introduced independently generated root, device, transport, MLS, application, and file keys with signed certificates, expiry, local revocation, and authenticated root rotation. This is separation at the primitive and wire layers, not a complete cryptographic channel ACL or a stronger human-identity claim. The Q4 proposal for short-lived delegated application keys remains unimplemented; v3 instead provides bounded wire-level deniability by removing transferable long-term-key authorship evidence from the outer frame.
- Contact-root trust anchors are not wired into `ContactPayload` or the GUI verification flow. A valid certificate proof and Noise-authenticated signature prove control of certified keys, not that the peer is the human contact you expect. Fingerprints must still be compared out of band.
- Revocation is a locally re-signed certificate bit. There is no distributed revocation service, directory, or real-time revocation propagation; a peer can continue presenting an old proof until a fresh one is exchanged.
- `Identity` remains `Clone`, so private-key material can be copied to multiple in-memory owners. Underlying libp2p key zeroization behavior is not guaranteed by this repository.
- New vaults store the complete encrypted identity bundle. Legacy transport-only imports bind fresh role keys and remain an explicit migration path, not an equivalent full-bundle restore.
- There is no multi-device account model or shared secret by default. P11 proves that two installations generate independent device keys and that an explicit portable encrypted export can restore the full role bundle; it does not provide seamless multi-device convergence or automatic contact migration.

## 2. Channel and group limitations

- Non-default channel text and receipts now use an independent derived `MlsChannelGroup` after signed, bound setup converges. An excluded parent member cannot decrypt that ciphertext even with parent MLS keys. This does **not** cover the default channel, which stays on the parent MLS group for compatibility.
- Channel create/rename/member policy (`CHN1`) still travels in the parent MLS group. Every parent member receives that metadata, and honest-client policy checks are not cryptographic access control for metadata. The derived group ID is a one-way identifier and does not itself encode an inverse parent/channel mapping; the signed `ChannelScope` supplies that binding for setup frames.
- P1e restores only **ready** derived channel groups. Incomplete setup groups have no authenticated application record and fail startup instead of reviving a partial boundary; setup KeyPackages, Welcomes, and decrypted channel text do not survive restart.
- The GUI now reports parent `CHN1` policy receipts separately from derived-group text readiness. Ready non-default text is labelled as a derived MLS boundary, default text as parent-group confidentiality, and incomplete setup as blocked; none of these labels claims a complete channel ACL.
- The application now has an integrated per-channel ratchet, epoch, replay state, and membership commits for non-default text, with authenticated encrypted restart continuity for ready groups and honest GUI status. Concurrent admin operations and policy metadata distribution remain application-level limitations; see `SECURITY_REMEDIATION_PLAN.md` for the P1 closeout.
- The creator is the only administrator. P6 adds local device-signed `RoleDelegation` primitives with expiry and conflict handling, but they are not wired into admin role changes, a directory, an enterprise policy engine, or the GUI trust-anchor flow. There is still no complete cryptographic role enforcement for concurrent admin operations.
- Setup and group-control frames have signed v2 transaction IDs, strict `(conversation_id, transaction_id, peer)` binding, and a bounded 512-entry in-memory cache of `(PeerId, SHA-256 digest)` pairs. Schema v4 adds a durable chained, blind-indexed digest log with a vault anchor: `Vault::unlock` verifies every authenticated record, chain link, blind index, and `<vault>/control.anchor`. `KeyPackageRequest` and `GroupJoinRequest` repeats stay idempotent; responses, Welcomes, `GroupWelcome`, `GroupCommit`, and all acks are non-repeatable. The log is capped at 4096 entries and fails closed when full or malformed. P3 binds durable exact-retry outcomes to channel context (parent and channel acks are not interchangeable) and adds durable outcomes for channel `Welcome`/`Commit`; v1 ack records remain readable. This is partial detection, not a replay-proof log: a full vault restored together with its anchor is not locally detectable, and state guards still carry the primary defense.
- Without an attached vault session, MLS group state, pending commits, key packages, ratchets, channels, and decrypted messages remain memory-only and restart loses them. With a session, ADR-0014 Phase 4 and P1e restore joined groups, ready derived channel groups, channel policy, bounded pending operations, receipt expectations, and queued ciphertext from authenticated encrypted records; parent setup KeyPackages/Welcomes, channel setup material, and decrypted messages still do not survive restart. The digest log is not a backup and does not restore OpenMLS state.

## 3. Storage and recovery limitations

- No encrypted backup/restore flow is implemented.
- Schema v4's chained control log and `<vault>/control.anchor` detect a database-only rollback and a tampered or missing anchor after a nonempty log. There is no external anchor: restoring the entire vault directory including the anchor is not locally detectable, and the digest log is not replay-proof.
- P4 gives new vaults a dedicated `Purpose::MlsState` HKDF key with a seven-salt profile and an authenticated `mls_key_version`. Legacy six-salt profiles remain on the general DB key; they are not bulk re-encrypted because their rows, chains, and anchor are authenticated together. Unknown key versions fail closed. This is key separation for MLS ciphertext, not an external rollback anchor or recovery of pending setup material.
- Windows ACL hardening is not implemented. Unix uses `0700`/`0600` and final-path symlink refusal for covered paths; quarantine creation also rejects ancestor symlinks and parent traversal. Vault parent-path symlinks and Windows reparse points remain gaps.
- File deletion is not cryptographic erasure on SSD, CoW, or snapshotting filesystems. The only reliable erasure story is destruction of the wrapping key.
- A fully compromised device can read decrypted messages in memory. No process isolation, secure enclave, or memory-locking mechanism is used.
- Repository-wide automated log-secret review is implemented as a static CI guard, but it cannot prove that every runtime path is free of secrets; it only rejects known unsafe macro and `Debug` derive patterns.

## 4. Network and anonymity limitations

- Direct connections expose IP addresses, connection timing, and packet sizes to peers and network observers.
- Concurrent pre-authentication handshakes are bounded (16 pending inbound and 16 pending outbound by default), and direct TCP sockets are limited to four simultaneous pre-auth upgrades per source IP by default using the same `max_connections_per_ip` value as established connections. This is not a distributed flood-capacity benchmark, and there is no OS file-descriptor tuning or guarantee against resource exhaustion from many source IPs. Relay upgrades are outside the raw-socket per-IP rule.
- Inbound application requests have an aggregate per-peer ceiling plus derived per-protocol reservations for message, setup, file, and control traffic. The reservations cannot exceed the configured aggregate ceiling, and a custom ceiling below four full frames falls back to that aggregate byte cap; this is single-peer DoS isolation, not a distributed-capacity guarantee. P13 adds a hostile-peer matrix test for oversized requests on every protocol, but it does not prove capacity under distributed floods or OS descriptor exhaustion.
- There is no verified Tor, onion-service, I2P, mixnet, or other anonymity route. P5's `TransportPrivacyMode::{Direct, TorRequired}` began as a fail-closed config boundary; Q5 now implements `TorRequired` as a SOCKS5-only outbound route with no direct listener/fallback, hostname proxy addresses rejected, and destination domains passed to the proxy. Proxy identity, reachability, real Tor behavior, DNS/IPv6/relay-reservation leak behavior, and packet-capture fallback proof remain unverified.
- Q2 pads MLS application plaintext to fixed buckets before encryption; it is coarse message-size normalization only. There is no randomized scheduling, heartbeat minimization, timing defense, or traffic-analysis resistance, and relays/peers still see outer frame sizes and buckets.
- Strong anonymity and protection against global traffic correlation are not claimed. A configured SOCKS5 route is not proof of anonymity.
- mDNS, Kademlia, identify, AutoNAT, DCUtR, relay, ping, and control observations are advisory. They do not establish contact trust, fingerprint verification, presence, capability, receipt, delivery, or reachability. SOCKS5 route mode disables mDNS, AutoNAT, and DCUtR through validation.
- Q1's `DialPolicy::RelayOnly` refuses direct application dials and direct listeners, requires observed relayed paths for application traffic, and hides the destination peer's direct view of the source IP. It does not hide metadata from the user-selected relay and is not onion routing.
- AutoNAT and DCUtR are best effort and are not universal NAT traversal.
- Relay operators observe PeerIds, IP addresses, circuit metadata, timing, and frame sizes and can deny service. They do not terminate Noise and do not receive application plaintext or file keys. File transfer over observed relayed paths is disabled for both outbound sends and inbound requests as a conservative policy, not because the relay can read the offer key.
- P7 replaces the normal typed file-path form with a native OS picker beside `Send`; feature-only builds honestly report `File picker requires the native build.` This improves local flow only. It adds no malware scanner, no transfer-after-restart claim, and no permission to send over a relay.
- Real two-machine LAN, NAT, mDNS, Kademlia, volunteer-relay, and real SOCKS5/Tor proxy verification has not been run on this host. The relay-only test uses a local relay; the SOCKS5 test uses a fake proxy.

## 5. Message delivery limitations

- The offline queue is ciphertext-only, capped at `MAX_OFFLINE_QUEUE` (16) entries, encrypted in the vault when a session is attached, and can be restored after restart; without a session it is in-memory and lost on restart or lock. A full queue returns `ChatError::OfflineQueueFull` before new ciphertext is composed, and oversized restored records fail closed. Restored entries remain unconfirmed until a verified receipt arrives.
- Transport `SentToPeer` is not delivery. Only verified MLS receipts from every expected member advance delivery state.
- Sequence gaps are not proof of malicious suppression: failed or abandoned outgoing messages intentionally create gaps.
- There is no decentralized mailbox or peer-operated store-and-forward protocol.
- Only bounded deniability is claimed. Legacy v2 outer Ed25519 signatures created transferable evidence of authorship, and that legacy codec/test is retained only as a compatibility artifact; production v3 wire bytes carry no long-term application signature or identity proof. A recipient or current group member with MLS state can still attribute a message, and a party holding a captured frame plus the epoch's MLS state is not denied that inference. There is no full metadata confidentiality, traffic-analysis resistance, or unlinkability. Q2 padding and Q3's v3 wire reduction do not hide IP, timing, direction, volume, outer bucket length, or route-tag linkability within one epoch.

## 6. File limitations

- Integrity verification means agreement with signed hashes. It does not mean a file is malware-free or safe to execute.
- The desktop application configures no real malware scanner. With no scanner, the status is `Unavailable` and release is denied.
- Structural validation is narrow and dependency-free for TXT, PNG, and GIF only. It is not a general MIME/format parser.
- Files are never auto-executed or auto-opened.
- Active file transfers now have an inactivity deadline and a local abort, and release cancellation is separate. The pinned libp2p request-response API cannot withdraw a request already queued in the transport worker; abort stops application progress and ignores late responses, but worker-side request state lasts until its normal response or connection failure. This is not a transport-level cancellation primitive.
- Malware scanning results from a scanner are only as trustworthy as that scanner.

## 7. Cryptographic agility limitations

- The cipher suite is fixed: `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.
- A pinned hybrid MLS KEM suite is enabled: `MLS_128_MLKEM768X25519_AES128GCM_SHA256_Ed25519` (`0x004F`) from the pinned OpenMLS draft feature on `openmls_rust_crypto`/`openmls_traits`. The sibling `0x004D` X-Wing suite is declared but unsupported by the pinned provider and is rejected. MLS signatures remain Ed25519 and libp2p Noise remains `Noise_XX_25519_ChaChaPoly_SHA256`, so this is not a post-quantum or quantum-resistance claim. The release candidate is not a production-stability claim; no custom cryptographic primitive is used.
- Protocol versions are explicit and unknown versions are rejected, but there is no negotiated downgrade-protection framework across all future algorithms.

## 8. Software supply-chain limitations

- CI uses locked builds and a security workflow/`deny.toml` are configured. Locally installed `cargo-audit 0.23.0` and `cargo-deny 0.22.1` now pass all advisory, license, ban, and source checks for both `Cargo.lock` and `fuzz/Cargo.lock`. `cargo audit` still reports non-failing unmaintained warnings (`paste`, `proc-macro-error2`, `zbus_names`, `zvariant`, `zvariant_derive`); these are residual maintenance risks, not evidence of compromise. The 2026-11-25 Security gates workflow passed all four jobs; this does not prove action-code trust, signed artifacts, or build provenance.
- The advisory fixes required moving to libp2p 0.57.1 (hickory-proto 0.26.4 through libp2p-mdns 0.49.0) and the OpenMLS 0.10.0-rc.1 provider stack (crypto-bigint 0.7.11). The GUI moved to egui/eframe 0.35 to resolve the `js-sys` graph conflict. Because the OpenMLS line is a release candidate, production stability and API longevity are not claimed; the choice is documented and locked, with all 207 workspace tests re-run after the change.
- Release artifacts have SHA-256 checksums, not developer signatures, provenance attestations, or notarization.
- Builds are not bit-for-bit reproducible.
- There is no auto-updater. Users must verify checksums through an authenticated release channel.
- External GitHub Actions are pinned to 40-character commit SHAs resolved from GitHub API refs on 2026-11-25, with source tag/branch comments retained; the `dtolnay/rust-toolchain` pins freeze the `stable`/`nightly` branch heads. This removes implicit mutable-ref movement but is not action-code review, signature verification, or build provenance; the 2026-11-25 CI runs are green.
- Deterministic SPDX SBOMs are generated from locked Cargo metadata and included in checksummed release artifacts, but they are source/lockfile inventories, not binary composition analysis, license legal review, build provenance, or vulnerability proof.
- Seven `cargo-fuzz` targets now exist, including `fuzz_v3_envelope` for the production v3 outer and inner parsers, and short local plain-libFuzzer smoke passes completed, but no long coverage-guided campaign has been run; deterministic legacy-`P2P1` mutation/truncation and v3 prefix-rejection tests remain the only deterministic mutation guards. Historical P12 re-ran audit/deny for both lockfiles, fuzz check/clippy/build, six 1000-input plain-libFuzzer smoke runs, and byte-identical 480-package SBOM regeneration on this host only; the final post-v3 gate passed all seven 1000-input smoke runs and byte-identical 489-package SBOMs. No signed release identity, build provenance, reproducible-build, CI, or release claim follows.

## 9. Production-readiness statement

This codebase has substantial tested cryptographic and local-security foundations, but the following prevent a production-ready security claim: only a partial application channel ACL (non-default text after bound setup; parent policy/default traffic remain outside it), role-separated identities whose contact-root trust anchors are not wired into GUI verification, unwired P6 delegation primitives, no persistence for setup material or decrypted messages, a bounded ciphertext-only offline queue rather than a mailbox, no replay-proof control frames, only partial rollback detection (database-only rollback and anchor tamper are detected; full vault including the anchor is not), a configured SOCKS5-only `TorRequired` route rather than a verified anonymity architecture, Q2 coarse padding and Q3 v3 wire reduction rather than full metadata confidentiality, bounded wire-level deniability with group-member attribution still possible, a hybrid MLS KEM suite with classical signatures and transport rather than post-quantum security, no delegated application keys, no real scanner configured, no signed release identity, and several platform-specific gaps. Treat it as a locally verified prototype with explicit hardening, not as an audited or anonymous messenger.
