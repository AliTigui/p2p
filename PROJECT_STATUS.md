### Post-v3 Q3/Q4 closeout (local only, not committed)

| Phase | Status | Claim boundary |
|---|---|---|
| Q3 | **Complete locally and uncommitted** | Production application wire is P2P3 `EnvelopeV3`; metadata reduction only, no complete metadata confidentiality or unlinkability. |
| Q4 | **Complete locally and uncommitted** | Bounded deniability on the v3 application wire; not ephemeral delegated keys and not full deniability or anonymity. |

Production application messages use `EnvelopeV3`: the outer header carries only `V3_MAGIC`/version, a per-epoch route tag, a random nonce, the wrapped body length, the wrapped MLS body, and an HMAC-SHA256 tag. Sender, conversation ID, epoch, message ID, sequence, timestamp, kind, and receipt bodies are in the MLS-protected inner frame. The MLS ciphertext is additionally wrapped with XChaCha20-Poly1305 under an exporter-derived AEAD key, and the outer tag is an exporter-derived HMAC-SHA256. The route tag is `SHA-256(domain separator || group ID || epoch)`, a local hint only; zero or ambiguous route matches fail closed. Legacy signed v2 application envelopes remain only as compatibility/adversarial tests, and production rejects v1/v2 application envelopes. Setup uses `/p2p-messenger/mls-setup/2` with a signed v4 `ciphersuite_id` at bytes 6..8; only `0x004F` is accepted, and v1–v3 setup frames are rejected.

The enabled hybrid MLS suite is `MLS_128_MLKEM768X25519_AES128GCM_SHA256_Ed25519` (`0x004F`) via a pinned OpenMLS draft feature on `openmls_rust_crypto`/`openmls_traits`; `0x004D` is declared but unsupported. MLS signatures remain Ed25519 and the Noise transport remains classical: this is not post-quantum/quantum-resistance, and no custom primitive is introduced. Q4 is bounded deniability, not ephemeral delegated application keys: the v3 wire has no transferable long-term-key authorship proof, but group members with MLS state can still attribute messages. SOCKS5/`TorRequired` remains configured route policy only; proxy identity, Tor behavior, and reachability are unverified. Relays/proxies still see IPs, timing, direction, volume, coarse lengths, and route-tag linkability within an epoch. No complete metadata confidentiality, unlinkability, or anonymity is claimed.

New dependencies are `hmac` + `sha2` in `p2p-messaging`, `p2p-crypto` in `p2p-groups`, and PQ crates transitively through both lockfiles. Named adversarial tests include `v3_wire_has_no_stable_sender_or_message_metadata`, `v3_mac_rejects_body_nonce_route_tag_and_version_tampering`, `v3_inner_frame_round_trips_and_rejects_tampering`, `every_v3_prefix_is_rejected_without_panics`, `v3_inner_replay_and_sequence_regression_are_rejected_after_decryption`, `v3_outgoing_sequence_is_consumed_only_after_a_successful_compose`, `pinned_openmls_advertises_the_enabled_hybrid_ciphersuite`, `hybrid_key_packages_and_welcomes_round_trip`, `v3_round_trip_hides_stable_metadata_from_third_parties`, `v3_rejects_tampering_wrong_route_legacy_wire_and_foreign_groups`, `v3_replay_and_sequence_regression_fail_after_decryption`, and `v3_route_tag_and_exporter_keys_are_epoch_bound`; the historical v2 test `signed_envelope_exposes_transferable_authorship_and_clear_metadata` is preserved as a compatibility/adversarial test. The GUI now has 30 checklist rows, including Key agreement, Message metadata, and Authorship deniability, with tests updated. Aggregate results for this post-v3 work are not restated here; see `SECURITY_TESTS.md` / the final report.

## Post-M13 durable control-log/anchor work (not a numbered milestone)

This is post-M13 durability work, **not Milestone 14**; Milestones 1–13 remain complete. Schema v4 adds transactional migrations with `control_log` (`sequence`, `record_bi`, `ciphertext`, `chain_hash`) and `control_state` (`id`, `sequence`, `chain`). Each AEAD record uses `Purpose::Db` and stores public PeerId bytes, the SHA-256 digest of an already authenticated signed MLS setup/group-control frame, and a repeatable flag; HMAC blind indexes support lookup. The `<vault>/control.anchor` is AEAD-protected with profile-bound AAD. `KeyPackageRequest` and `GroupJoinRequest` are idempotent/repeatable; Welcomes, commits, responses, acks, and all other setup/group frames are non-repeatable. The log is capped at 4096 records and fails closed.

`Vault::unlock` verifies every record, chain continuity, blind indexes, and the anchor; a database older than the anchor and anchor tampering are detected. Restoring the entire vault **including** the anchor is not locally detectable, and no external anchor exists. This is partial rollback detection, not a replay-proof or rollback-proof log.

`MessengerController::start_with_control_log` attaches a cloned vault `Session` (the GUI passes `session.try_clone()`) and requires the vault identity to match the controller identity. The post-M13 control-log work itself does **not** restore OpenMLS group/ratchet state or pending key packages; the anchor is not a backup. ADR-0014 Phase 4 now restores explicitly `Joined` groups, encrypted channel policy, bounded pending operations, receipt expectations, channel acknowledgement state, and offline queued ciphertext from authenticated records through that attached session; decrypted messages remain memory-only. ADR-0013 records the control-log design, and `SECURITY_AUDIT.md` now records 20 findings, including SA-020 for the residual full-vault rollback limitation.

## ADR-0014 Phases 1–3 encrypted MLS state storage, anchor, and provider, plus Phase 4 core restore slice (schema v5, not a milestone)

ADR-0014 is accepted as a phased design. Phase 1 adds `crates/storage/src/mls_state.rs`, schema-v5 `mls_groups`/`mls_state` tables, bounded encrypted CRUD for opaque provider values, HMAC blind indexes, per-group SHA-256 chains, and unlock-time verification. Values are AEAD-encrypted under the existing `Purpose::Db` subkey with versioned, profile-bound AAD; blind indexes use `Purpose::BlindIndex`. A dedicated `Purpose::MlsState` is deferred because it would require a stored-salt-slot migration for existing vaults. Password changes still re-wrap only the master key and do not bulk re-encrypt MLS state.

Phase 1 caps one value at 1 MiB, the store at 4,096 entries, and the group set at 64 groups; caps and integrity failures fail closed. Phase 2 extends `<vault>/control.anchor` to a version-2 AEAD record that keeps the control-log sequence/chain and adds a bounded, authoritative `group_blind_index -> (epoch, state_chain)` map. `Vault::unlock` now verifies every MLS row, blind index, epoch binding, group chain, and exact anchor watermark map; database-only rollback before an MLS write or before an explicit deletion fails with `RollbackDetected`. A v1 anchor is migrated after both databases verify. MLS writes install the anchor before committing, so an interrupted write fails closed instead of blessing older state; control-log appends remain database-first with bounded anchor catch-up. Restoring the whole vault including the anchor remains undetectable, as before.

Phases 1–2 added encrypted storage and the anchor only. Phase 3 adds `StagedMlsProvider` in `crates/storage/src/mls_provider.rs`: an `openmls_traits::StorageProvider` adapter that stages all writes in memory, exposes staged values to reads, discards on cancellation, and flushes the whole set as one SQLite transaction with anchor advancement and staged tombstones. A real `MlsGroup::new_with_group_id` / `MlsGroup::load` round trip after reopen is covered by `crates/storage/tests/mls_provider.rs`.

Phase 4 wires that provider into the application. `crates/groups` adds a vault-backed `MlsProvider` with storage-backed constructors and `MlsConversation::load_with_storage`, which calls `MlsGroup::load` through the encrypted provider and verifies group id, local membership, and local signature key. `MessengerController::build` loads all vault group ids when a `Session` is attached (no-session constructors stay memory-only) and restores only explicitly `Joined` conversations. Application policy is an authenticated version-2 record under the storage label `p2p.app.conversation/v1` and the group blind index; it carries status, admin/members, channels with last-frame pointers, active channel, MLS epoch, next sequence, pending-operation detail, receipt expectations, non-delivered outgoing states, and queued ciphertext, and is rewritten after every relevant controller mutation (setup, join, status changes, channel create/rename/membership, active-channel selection, group membership changes, pending-operation progress/completion, send/retry/receipt progress, inbound CHN1 policy, local removal). Legacy v1 records stay readable; a v1 pending flag fails closed because it has no authenticated payload. Restore validates record epoch, conversation ID, group membership, peer identities, bounded counts/sizes, queue envelope signature and conversation/message binding, and pending-operation transaction/member/target consistency; anything inconsistent fails startup with `ChatError::MlsRestore`. Non-`Joined` records remain encrypted but are skipped. Restored outgoing states are limited to `Queued`/`SentToPeer`, so a verified receipt is still required for `Delivered`; decrypted text is never restored. Local removal also deletes that group's encrypted MLS state. The GUI's `start_chat` now returns startup errors, so a restore failure becomes a real `VaultState::Failed` instead of an unlocked view with fabricated status. The Phase 4 hardening pass also rejects a vault/controller or KeyPackage identity mismatch, keeps the reserved global provider bucket out of `mls_group_ids()`, prunes removed-member receipt/queue state, and stores encrypted per-request outcomes so byte-identical group-commit and group-Welcome retries after restart return the original ack without re-applying an epoch transition.

## Stack decision change (Milestone 1)
The original brief specified Tauri 2 + React + TypeScript + Vite. The user asked why npm/TypeScript/browser were needed and chose a **pure Rust GUI**. ADR-0006 records this and supersedes ADR-0005. The application has no webview, browser engine, JavaScript, npm, Node.js, React, or TypeScript.

- `crates/files` (Milestones 7 and 8):
  - Bounded signed `FILE` frames: fixed magic/version, seven codes (`Offer`, `Accept`, `Chunk`, `ChunkAck`, `Manifest`, `ManifestAck`, `Reject`), 16-byte transfer ID, sender public key/PeerId, and Ed25519 signature. Malformed, oversized, wrong-magic/version, wrong-peer, tampered, and trailing-byte frames fail closed.

  - Bounds: file name ≤ 255 UTF-8 bytes with no path separators or control characters, plaintext ≤ 64 MiB, chunk plaintext ≤ 256 KiB, at most 256 chunks, signed frame ≤ 1 MiB.

## Security concerns
- MLS payload encryption and the signed setup exchange are implemented and tested for two- and three-member groups through the Rust API, wire test, controller tests, and GUI path. The GUI shows real observed setup/group/delivery state and does not claim verification or delivery by itself.
- M9 admin policy remains application-level and local in the shipped GUI: the creator is the initial admin, and only that authenticated PeerId may add, remove, or refresh keys. It is not a complete cryptographic role system. P6 adds local device-signed delegation primitives with conflict/expiry handling, but they are not wired into a directory, enterprise policy engine, GUI trust anchor, or admin role change. A compromised admin key still authorizes those operations.
- M10 channel policy remains application-level and local: the creator/admin may create, rename, and set channel members, and clients verify signed parent MLS policy frames and sequential revisions. P1d puts non-default text and receipts in a signed, bound derived MLS group so an excluded parent member cannot decrypt that channel ciphertext; parent policy metadata and default-channel traffic remain on the parent MLS group. This is not a complete cryptographic channel ACL. P6 delegation primitives remain unwired, and replay of custom channels to later joiners is not implemented.
- Decrypted messages are memory-only and never written in plaintext. With an attached vault `Session`, ADR-0014 Phase 4 restores explicitly `Joined` MLS group state, encrypted channel policy, bounded pending operations, receipt expectations, channel acknowledgement state, and offline queued ciphertext on startup; without a session, MLS state stays memory-only as before. Setup KeyPackages and Welcome material still must remain in the same running session; a legacy v1 pending flag fails startup rather than resuming an unauthenticated operation.
- The offline queue holds signed MLS ciphertext only and is capped at `MAX_OFFLINE_QUEUE` (16). With an attached vault `Session` it is encrypted in the local database and restored after restart; without one it remains memory-only. A full queue returns `ChatError::OfflineQueueFull` before new ciphertext is composed, and an oversized restored record fails closed. Queueing and restore never write plaintext to SQLite; tests scan the database, WAL, and SHM for the queued sentinel.
- The legacy `Conversation::load` path parses receipt bodies from raw payloads and cannot rebuild MLS receipts. `MlsConversation::load_with_storage` restores MLS group state through the encrypted provider, not from envelope records; receipt expectations are restored from the authenticated application record, while decrypted text is not restored.
- A valid envelope/setup signature proves control of the certified `Application` role key, a valid file frame proves control of the certified `File` role key, and the Noise-authenticated peer is bound to the certified `Transport` key through the identity proof; none proves the person is the intended contact. Fingerprints must be compared out of band. The historical P10 signed v2 application envelopes exposed transferable authorship evidence and clear metadata; production P2P3 application envelopes instead carry no transferable long-term-key authorship proof, but this is bounded deniability only: group members with MLS state can still attribute messages, and no full deniability, metadata-confidentiality, unlinkability, or anonymity claim is made. M12 caps pasted contact URIs and query fields before decoding, and caps imported identity envelopes before header or parameter parsing.
- Setup and group-control frames are production signed v4 frames on `/p2p-messenger/mls-setup/2` with a random 16-byte transaction ID bound to the authenticated peer and certified `Application` role key; the signed `ciphersuite_id` at bytes 6..8 accepts only `0x004F`. Pending key packages, Welcomes, commits, retries, and acknowledgements are matched on channel-aware outcome keys derived from conversation/channel context, transaction ID, and peer; stale, substituted, cross-transaction, cross-channel, and legacy v1–v3 setup frames are rejected. A bounded 512-entry memory-only cache of `(PeerId, SHA-256 digest)` pairs suppresses exact authenticated replays of terminal frames, while KeyPackage and GroupJoin request repeats stay idempotent so a lost response can be retried. The cache stores no frame bodies and is not durable or replay-proof on its own; its eviction window is supplemented by the durable log below for exact authenticated control frames. The post-M13 control log persists only public PeerId bytes, SHA-256 digests of already authenticated signed frames, and a repeatable flag in 4096 bounded AEAD records under `Purpose::Db` with HMAC blind indexes. `Vault::unlock` detects a database older than the profile-bound-AAD anchor and anchor tampering, but a full vault restore including the anchor is not locally detectable and no external anchor exists. The log/anchor do not restore OpenMLS group/ratchet, pending key-package, or channel state, and the anchor is not a backup.
- Group commits are merged locally and remain pending until required acknowledgements are verified. A disconnected required member can leave an operation pending; the UI reports that honestly and does not time out, roll back, or claim completion.
- A removed member stays on the excluded MLS epoch and cannot decrypt future group traffic. Stale-epoch ciphertext from that member is rejected by remaining members. No member can be added without a direct connection and a validated KeyPackage.
- Group text is delivered only after receipts from every expected member. One disconnected recipient holds the operation's ciphertext copy and prevents `Delivered`; a vault-backed queue survives restart, but decrypted text never does.
- Direct connect and all four application protocols, including M13's opaque control protocol, are implemented and tested. `MessageEvent`, `SetupEvent`, `FileEvent`, and `ControlEvent` use redacted `Debug` output that reports lengths but never opaque request/response bytes. Identify and ping remain off by default; when identify is explicitly enabled, protocol/agent strings are bounded and listen addresses are hidden, but the protocol list is still not cross-checked by the application.
- Explicit libp2p pending-socket caps now bound concurrent inbound and outbound handshakes before Noise authentication; authenticated global/per-peer/per-IP limits, duplicate-dial rejection, and sliding-window request/byte budgets remain in place. Expired rate-limiter peer entries are removed, and a peerless transport failure is reported as an event without overwriting cached live connections. These controls do not authenticate the human behind a PeerId, prevent Sybil identities, hide metadata, or replace application-level authorization. The per-IP pre-auth cap applies to raw direct TCP sockets; relay upgrades and distributed floods remain outside that local admission rule.
- File transfer is bound to 64 MiB total, 256 KiB chunks, 256 chunks, and one active transfer per peer in a joined conversation. Active transfers have an inactivity deadline and `abort_file`; `ReleaseApproval::Cancelled` applies only to a verified transfer and blocks release. An already queued worker request cannot be withdrawn through the pinned transport API, so abort ignores late responses instead.
- The file content key is protected by end-to-end Noise and is never persisted. No relay is configured by default. M13 relay support is opt-in; the pinned libp2p relay forwards opaque Noise-protected bytes and does not see the framed offer or content key. File transfer is explicitly refused on observed relayed connections as a conservative metadata/policy choice until a dedicated relay-safe file-key/transport design exists.
- `IntegrityVerified` means the bytes matched the signed SHA-256 manifest only. It is not malware safety, format validation, or a scan result. `ScanStatus` is `NotApplicable` before verification and starts as `Unavailable` afterward.
- The M8 scanner interface is application-supplied and returns exact categories. Only `SecurityConfig::scan` can create a `ScanOutcome`, including its private validated `FileFormat`. The desktop app configures no scanner, so it never displays a clean scan result.
- Structural validation supports TXT (UTF-8 without disallowed control bytes), PNG (signature, chunk lengths, CRC, IHDR, IEND), and GIF (header, color tables, blocks, trailer). A claimed-format mismatch returns `UnsupportedFormat` before a scanner is invoked. These checks are not malware detection, general media parsing, or MIME sniffing.
- Policy release requires a validated format, clean scanner outcome, cross-platform safe base name, non-empty bounded size/chunk count under an unraisable 64 MiB cap, explicit extension allowlist, and explicit per-file `Approved` status. Released bytes are returned only in a zeroizing `ReleasedFile`; the release path writes no plaintext. The desktop app copies them into the encrypted attachment store, and the native save helper used by the OS dialog is the only plaintext disk write: it sanitizes the suggested name, refuses a pre-existing symlink, creates `0600` files on Unix, syncs bytes, and reports only static errors.
- `ReleaseApproval::Cancelled` is terminal for release of a verified transfer. It does not delete verified quarantine ciphertext and does not affect an active transfer; active transfers use the deadline or `abort_file` instead. Quarantine deletion defaults to `Retain`; under `Explicit` it requires a verified transfer that was released or cancelled. Stored-attachment deletion is a separate explicit action and now checks the blob path for symlinks before removing its database record. Filesystem deletion is not secure erasure on SSD/CoW storage.
- Attachments use a random per-file key wrapped under `storage/attachments`, an HMAC blind index, encrypted metadata, and a SHA-256 recheck on read. Read and explicit delete both reject symlinked blob paths, and delete checks before removing the record. Raw DB/WAL/SHM/blob sentinel scans cover names, payloads, and format labels. Windows ACL hardening remains a target.
- Vault encryption at rest is tested on Unix by scanning `profile.db`, `profile.db-wal`, and `profile.db-shm` for plaintext sentinels and raw private-key bytes. Restricted directory permissions, final-path symlink refusal, and quarantine ancestor/parent-component checks are enforced on Unix only.
- Argon2id runs on a dedicated `std::thread` per vault operation. The network worker owns its own Tokio current-thread runtime; there is not yet one shared application Tokio runtime with a blocking pool.
- Password-guessing resistance depends on the user's passphrase. Forgetting the password means permanent data loss; there is no escrow or recovery promise.
- The vault directory is under the OS local-data directory (`~/.local/share/p2p-messenger` on Linux) or a local fallback; the UI shows the real path.
- Default bootstrap, relay, discovery, identify, ping, AutoNAT, and DCUtR settings are empty/off everywhere; no developer-operated service is configured.
- M13 discovery events are advisory candidates only: no auto-dial, contact save, fingerprint verification, or delivery claim follows from mDNS/Kademlia. Relay events are transport observations only; relay operators can see IPs, timing, and sizes and can deny service. AutoNAT/DCUtR results are best-effort, not universal NAT reachability.
- M13 control frames are opaque transport observations. The controller drains them but derives no presence, capability, delivery, trust, or safety state. `NetworkPrivacyStatus` separates configured flags/counts from counters and strings changed only by real libp2p events; cumulative reservation, circuit, and identify values are labelled as observed since startup, while relayed connections are the latest live transport observation.
- Identify, when explicitly enabled, hides listen addresses and bounds peer-provided strings, but it still reveals a protocol/agent description and does not authenticate the human behind the PeerId. There is no Tor/I2P/mixnet, anonymity, complete metadata confidentiality, unlinkability, or proxy-identity claim; post-v3 relays/proxies still see IPs, timing, direction, volume, coarse lengths, and route-tag linkability within an epoch.
- GUI shows real observed connection state and explicit "Not configured"/"Not implemented" rather than fake connected, verified, delivered, or clean states.
- Release packages are unsigned by default and macOS DMGs are not notarized. `SHA256SUMS` verifies artifact integrity against the release channel, not developer identity or malware safety. Signing is operator-controlled and no signing secret is stored in the repository. There is no auto-updater, telemetry, or phone-home endpoint.
- The native window was built successfully but not visually inspected on this headless host (no display server). CI and a desktop host should do the visual check.

## Important architectural decisions
- ADR-0001: no mandatory centralized infrastructure; direct connect works with zero bootstrap peers.
- ADR-0002: every conversation, including 1:1, is an MLS group.
- ADR-0003: password wraps a random master key; domain-separated subkeys; password change never bulk re-encrypts data.
- ADR-0004: initial identities are device-specific, portable only via explicit encrypted export/import.
- ADR-0005: superseded.
- ADR-0006: pure Rust GUI with egui/eframe; no npm/TypeScript/webview.
- ADR-0007: separate signed file protocol, fresh direct-only content key, bounded AEAD chunks, signed manifest commitment, ciphertext-only quarantine, narrow format validation, explicit approval before release, encrypted attachment storage, user-chosen native OS save, explicit deletion policies, and no clean/safe status without an independent scanner.
- ADR-0008: extend the existing signed `MLS1` protocol with bounded group-control frames; creator-as-admin policy; locally merged commits with pending acknowledgement state; Welcome-based join; all-member delivery receipts; no fourth wire protocol.
- ADR-0009: channels are bounded `CHN1` application bodies inside one MLS group; `channel_id` is in authenticated MLS plaintext; creator-as-admin channel policy with local membership enforcement; legacy receipts; no new wire protocol, new MLS group, or cryptographic channel ACL.
- ADR-0010: source-first cross-platform release packaging with native runners, portable archives plus platform installers, checked checksums, optional operator-controlled signing, no auto-updater/telemetry, and no mandatory centralized infrastructure.
- ADR-0011: M12 hardening chooses bounded, testable local safety checks and honest non-claims over unverifiable Windows ACL/secure-erasure promises.
- ADR-0012: M13 optional discovery, relay, NAT, identify, and control capabilities remain off by default; observations are advisory and are never promoted to trust, contact verification, delivery, or anonymity claims.
- ADR-0013: post-M13 schema v4 durable control-log digests with a chained, AEAD-protected, profile-bound anchor provide partial rollback detection only; they do not restore MLS state and cannot detect a full vault-plus-anchor restore.
- ADR-0014: accepted phased plan for a vault-backed encrypted OpenMLS `StorageProvider`. Phases 1–2 implement schema-v5 opaque MLS-value storage with versioned `Purpose::Db` AAD, blind indexes, per-group chains, unlock verification, and a v2 anchor with authoritative MLS watermarks. Phase 3 implements the staged provider adapter with atomic flush, tombstones, and a tested `MlsGroup::load` round trip. Phase 4 restores joined MLS groups, encrypted channel policy, bounded pending operations, receipt expectations, and offline queued ciphertext through the controller with honest GUI failure states; setup KeyPackage/Welcome and decrypted-message restore remain design follow-ups. No numbered milestone, wire format, or mandatory infrastructure is introduced.
- `libp2p` is pinned to `=0.57.1` with `libp2p-request-response =0.30.0`. The earlier 0.57 conflict is resolved by using egui/eframe 0.35, whose `js-sys ^0.3.77` requirement is compatible with `libp2p-swarm 0.48.0`'s exact `wasm-bindgen-futures =0.4.58`. The codec was migrated to the RPITIT `Codec` trait without changing bounded framing.
- OpenMLS `0.10.0-rc.1` with provider/traits `0.7.0-rc.1` is pinned because it carries crypto-bigint 0.7.11 and clears RUSTSEC-2026-0387; this is a Phase 0 remediation choice, not a production-readiness claim. `openmls_sqlite_storage` was validated but not enabled because SQLite storage of MLS secrets would violate encrypted-at-rest requirements without another encryption layer.
- MLS setup/group control and file transfer are separate versioned protocols, not message kinds. Setup and group-control frames share the same signed `MLS1` protocol and codec; the transport never interprets their bytes, and `p2p-chat` verifies signatures and authenticated peers before MLS or file state changes.
- `rfd 0.18.0` was validated (MIT, MSRV 1.92, current docs.rs/repository) and is an optional native-only dependency; cancelled save dialogs write nothing.
