## Current milestone

Milestones 1–10 established the implemented foundation. Milestone 5 covers canonical signed envelopes, replay/sequence checks, MLS ciphertext and encrypted receipts, ciphertext-only persistence, two explicit request-response protocols (`/p2p-messenger/message/1` and `/p2p-messenger/mls-setup/1`), signed KeyPackage/Welcome/Ack setup frames, an application controller, and the native GUI path. Milestone 6 adds the in-memory offline queue, reconnect-triggered retry, bounded automatic redial/backoff, honest retry state, duplicate-dial rejection, connection admission limits, and sliding-window per-peer request/byte budgets. Milestone 7 adds a third bounded protocol (`/p2p-messenger/file/1`), `p2p-files`, fresh per-transfer XChaCha20-Poly1305 keys, 256 KiB chunks, SHA-256 manifest commitments, restricted ciphertext-only quarantine, joined-conversation transfer gating, one active transfer per peer, and an honest file-status list in the GUI.

Milestone 8 adds `p2p-security` with an application-supplied `FileScanner`, exact result categories, a private `ScanOutcome` boundary, dependency-free TXT/PNG/GIF structural validation, a conservative allowlist policy, `ReleaseApproval`, explicit approval/cancellation, and a zeroizing in-memory `ReleasedFile`. It also adds schema v3 encrypted attachments in `p2p-storage`, explicit quarantine deletion in `p2p-files`/`p2p-chat`, a native-only `rfd` save dialog in the desktop app, and the required UI/model rows.

Milestone 9 extends the existing signed `/p2p-messenger/mls-setup/1` protocol with bounded group-control frames for Add, Remove, self-Update, commits, acknowledgements, and group Welcomes; no fourth wire protocol was added. The creator is the initial admin, and only the admin may start group operations. Commits are merged locally and broadcast to required existing members, with `pending_operation` blocking messages and further changes until all required acknowledgements arrive. A new member joins at the commit's new epoch through its Welcome and is excluded from that Add commit's acknowledgement set. Group text is one signed MLS envelope broadcast to every current member; local `Delivered` requires receipts from all expected members.

Milestone 10 reuses the reserved `MessageKind::Channel` code and a bounded `CHN1` application codec. `channel_id` is inside MLS application plaintext, not the envelope header; no envelope v2, setup code, new MLS group, or new external dependency was added. Every joined conversation starts with `[0; 16]`/`general`. The admin may create, rename, and set members of channels; allowed MLS members may post text, which is sent only to allowed recipients. Channel membership is local policy, not a cryptographic ACL, because all group members hold group keys. Offline queue, receipt-gated delivery, and all three wire protocols are unchanged. No configured scanner, general format/MIME parsing, read-receipt UI, role delegation, cryptographic per-channel keys, or encrypted MLS persistence exists yet. No discovery, relay, account, or developer-operated infrastructure is used.

Milestone 11 adds source-first release engineering without changing the application runtime. `.github/workflows/build.yml` builds `p2p-desktop --features native --release --locked` on Linux x86_64, Windows x86_64 MSVC, macOS x86_64, and macOS arm64. `packaging/` produces portable archives plus `.deb` (Linux), `.msi` (Windows, WiX 3.14+), and `.dmg` (macOS, `hdiutil`). Each package includes `README.md` and `NOTICE.md`; tagged `v*` releases add a verified `SHA256SUMS` manifest. Signing is optional and operator-controlled (`WINDOWS_SIGNING_THUMBPRINT`, `MACOS_SIGNING_IDENTITY`); packages are unsigned and macOS DMGs are not notarized by default. GitHub Releases are only an optional download host: there is no auto-updater, telemetry, account service, discovery service, relay, or phone-home endpoint. Windows/macOS builds and downloaded artifact integrity/structure were verified on GitHub runners and this Linux host on 2026-11-25; MSI/DMG installation, signing, notarization, and visual GUI inspection remain platform-host tasks.

Milestone 12 adds concrete local security hardening without a new dependency, wire protocol, or data format. Release names are rejected unless they are safe base names on all supported platforms (including trailing dot/space and Windows device names), and the release byte cap is enforced even if a caller supplies a larger policy. The native OS save path sanitizes the suggested name, refuses a pre-existing symlink, creates files as `0600` on Unix, writes bytes with `sync_all`, and reports only static errors. `Vault::open` and quarantine directory creation refuse symlinked final paths on Unix; attachment reads still refuse symlinks, and attachment deletion now checks the blob path before removing the database record. `MessageEvent`, `SetupEvent`, and `FileEvent` use hand-written redacted `Debug` implementations so opaque request/response bytes are never printed. Contact URI and encrypted identity envelope imports enforce byte caps before PeerId parsing, percent-decoding, base64 decoding, or KDF/header work. Filesystem deletion is still not secure erasure, and Windows ACL hardening remains unimplemented.

Milestone 13 adds optional network privacy and discovery controls without changing the default zero-infrastructure path. `NetworkConfig` now supports user-enabled identify, ping, mDNS, Kademlia with user-supplied direct bootstrap addresses, relay client/server mode with user-supplied direct relay addresses, AutoNAT, DCUtR, and a bounded relayed-connection cap; all are off/empty by default and apply only when the worker starts. Discovery candidates are advisory only: they are never auto-dialed, trusted, or promoted to contacts or fingerprint-verified peers. Relay operators can observe PeerIds, IPs, timing, and sizes and can deny service; relayed connections are bounded and counted from real transport observations. With the pinned libp2p stack, the relay transport receives the same Noise upgrade as direct TCP and forwards opaque bytes, so it does not see the signed file offer or the fresh content key. File transfer over an observed relayed path is nevertheless refused as a conservative policy until a dedicated relay-safe file-key/transport design exists. A new `/p2p-messenger/control/1` request-response protocol uses the same bounded opaque codec; the controller drains control frames but derives no capability, presence, receipt, or delivery state from them. `NetworkPrivacyStatus` separates local configuration from observed facts, identify strings are bounded and listen addresses hidden, and the GUI shows honest limitation rows. No strong anonymity, Tor/I2P/mixnet, universal NAT traversal, metadata confidentiality, or centralized infrastructure is claimed.

## Post-M13 durable control-log/anchor work (not a numbered milestone)

This is post-M13 durability work, **not Milestone 14**; Milestones 1–13 remain complete. Schema v4 adds transactional migrations with `control_log` (`sequence`, `record_bi`, `ciphertext`, `chain_hash`) and `control_state` (`id`, `sequence`, `chain`). Each AEAD record uses `Purpose::Db` and stores public PeerId bytes, the SHA-256 digest of an already authenticated signed MLS setup/group-control frame, and a repeatable flag; HMAC blind indexes support lookup. The `<vault>/control.anchor` is AEAD-protected with profile-bound AAD. `KeyPackageRequest` and `GroupJoinRequest` are idempotent/repeatable; Welcomes, commits, responses, acks, and all other setup/group frames are non-repeatable. The log is capped at 4096 records and fails closed.

`Vault::unlock` verifies every record, chain continuity, blind indexes, and the anchor; a database older than the anchor and anchor tampering are detected. Restoring the entire vault **including** the anchor is not locally detectable, and no external anchor exists. This is partial rollback detection, not a replay-proof or rollback-proof log.

`MessengerController::start_with_control_log` attaches a cloned vault `Session` (the GUI passes `session.try_clone()`) and requires the vault identity to match the controller identity. This work does **not** restore OpenMLS group/ratchet state, pending key packages, or channel state; runtime MLS state remains memory-only (ADR-0014 Phases 1–3 add unwired encrypted storage, anchor watermarks, and a staged `StorageProvider` adapter), and the anchor is not a backup. ADR-0013 records the design, and `SECURITY_AUDIT.md` now records 20 findings, including SA-020 for the residual full-vault rollback limitation.

## ADR-0014 Phases 1–3 encrypted MLS state storage, anchor, and provider (schema v5, not a milestone)

ADR-0014 is accepted as a phased design. Phase 1 adds `crates/storage/src/mls_state.rs`, schema-v5 `mls_groups`/`mls_state` tables, bounded encrypted CRUD for opaque provider values, HMAC blind indexes, per-group SHA-256 chains, and unlock-time verification. Values are AEAD-encrypted under the existing `Purpose::Db` subkey with versioned, profile-bound AAD; blind indexes use `Purpose::BlindIndex`. A dedicated `Purpose::MlsState` is deferred because it would require a stored-salt-slot migration for existing vaults. Password changes still re-wrap only the master key and do not bulk re-encrypt MLS state.

Phase 1 caps one value at 1 MiB, the store at 4,096 entries, and the group set at 64 groups; caps and integrity failures fail closed. Phase 2 extends `<vault>/control.anchor` to a version-2 AEAD record that keeps the control-log sequence/chain and adds a bounded, authoritative `group_blind_index -> (epoch, state_chain)` map. `Vault::unlock` now verifies every MLS row, blind index, epoch binding, group chain, and exact anchor watermark map; database-only rollback before an MLS write or before an explicit deletion fails with `RollbackDetected`. A v1 anchor is migrated after both databases verify. MLS writes install the anchor before committing, so an interrupted write fails closed instead of blessing older state; control-log appends remain database-first with bounded anchor catch-up. Restoring the whole vault including the anchor remains undetectable, as before.

Phases 1–2 added encrypted storage and the anchor only. Phase 3 adds `StagedMlsProvider` in `crates/storage/src/mls_provider.rs`: an `openmls_traits::StorageProvider` adapter that stages all writes in memory, exposes staged values to reads, discards on cancellation, and flushes the whole set as one SQLite transaction with anchor advancement and staged tombstones. A real `MlsGroup::new_with_group_id` / `MlsGroup::load` round trip after reopen is covered by `crates/storage/tests/mls_provider.rs`. Phase 3 does **not** add controller/GUI wiring, `MlsGroup::load` use by the application, channel/pending-operation restore, or application-policy restore; runtime application MLS state remains memory-only. Phase 4 (controller/GUI restore and policy reapplication) is not started.

  - The sender public key is included because a PeerId is a multihash and cannot independently verify an Ed25519 signature; it is bound to the signed bytes and checked against the declared PeerId.
  - `verify_envelope` performs non-mutating pre-decryption checks; `receive_with_plaintext` records an envelope only after the MLS layer supplies the decrypted application body. The legacy `receive` path remains for opaque/test payloads.
  - Bounded replay cache with message-ID deduplication and strict per-sender sequence high-water marks. Replay, sequence regression, wrong conversation, and epoch mismatch are rejected before state changes.
  - Delivery state machine: `Composed → Queued → SentToPeer → Delivered → Read`, plus `Failed`. `SentToPeer` is explicitly unconfirmed and is never shown as `Delivered`.
  - `MessageKind::Channel` has fixed envelope code `8` and round-trips through signed envelope encoding; its body remains opaque MLS application ciphertext at this layer.
  - Canonical receipt body codec (`Delivered`/`Read`) with explicit transition rules; `MlsConversation::receipt` encrypts that body into an MLS application message.
  - Ciphertext-only vault persistence via schema v2; envelopes are reverified on load. The legacy loader cannot rebuild MLS receipts because MLS state is not persisted; this is documented.

- `crates/files` (Milestones 7 and 8):
  - Bounded signed `FILE` frames: fixed magic/version, seven codes (`Offer`, `Accept`, `Chunk`, `ChunkAck`, `Manifest`, `ManifestAck`, `Reject`), 16-byte transfer ID, sender public key/PeerId, and Ed25519 signature. Malformed, oversized, wrong-magic/version, wrong-peer, tampered, and trailing-byte frames fail closed.
  - Fresh random 32-byte content key per transfer, carried only in the signed offer over Noise and held in zeroizing memory. It is never written to quarantine and `Debug` redacts it.
  - Bounds: file name ≤ 255 UTF-8 bytes with no path separators or control characters, plaintext ≤ 64 MiB, chunk plaintext ≤ 256 KiB, at most 256 chunks, signed frame ≤ 1 MiB.
  - XChaCha20-Poly1305 per chunk with fresh nonce and AAD binding `p2pmsgr-file-chunk-v1`, transfer ID, index, chunk count, and exact plaintext length. Out-of-order, duplicate, truncated, and tampered chunks fail closed.
  - SHA-256 per chunk and over the full plaintext, plus a domain-separated manifest commitment signed in the offer. Verification recomputes all hashes in bounded zeroizing memory and rejects manifest substitution, missing chunks, length mismatch, and hash mismatch.
  - Ciphertext-only quarantine in a `0700` directory with `0600` chunk files on Unix; the manifest record contains hashes and public metadata only. No plaintext or content key reaches disk. Quarantine creation rejects ancestor symlinks and parent traversal on Unix; Windows reparse points and vault parent-path symlinks remain unaddressed.

## Security concerns
- MLS payload encryption and the signed setup exchange are implemented and tested for two- and three-member groups through the Rust API, wire test, controller tests, and GUI path. The GUI shows real observed setup/group/delivery state and does not claim verification or delivery by itself.
- M9 admin policy is application-level and local: the creator is the initial admin, and only that authenticated PeerId may add, remove, or refresh keys. It is not a cryptographic role system, and role delegation is not implemented. A compromised admin key still authorizes those operations.
- M10 channel policy is also application-level and local: the same admin may create, rename, and set channel members, and clients verify signed MLS application frames and sequential revisions. Channel membership does not create an MLS group boundary. Every MLS group member holds the group keys, so an excluded member could decrypt channel ciphertext it obtains; restricted sends only omit that member from ordinary delivery. Per-channel MLS keys, role delegation, and replay of custom channels to later joiners are not implemented.
- MLS group state, pending operations, and decrypted messages are memory-only: they are never written to disk in plaintext, but they are lost on restart. KeyPackages, Welcomes, commits, and acknowledgement state must remain in the same running session as the operation.
- The offline queue holds signed MLS ciphertext only and is lost on restart or lock. It has no vault/storage handle, so queueing cannot write plaintext to SQLite; the integration test scans the database, WAL, and SHM for the queued sentinel.
- The legacy `Conversation::load` path parses receipt bodies from raw payloads and cannot rebuild MLS receipts. `MlsConversation` has no load path; treating encrypted envelope records as a restored MLS conversation would be incorrect.
- A valid envelope, setup, or file signature proves the sender controls the bound Ed25519 key and is the authenticated Noise peer; it does not prove the person is the intended contact. Fingerprints must be compared out of band. M12 caps pasted contact URIs and query fields before decoding, and caps imported identity envelopes before header or parameter parsing.
- Setup and group-control frames are signed v2 `MLS1` frames with a random 16-byte transaction ID bound to the authenticated peer. Pending key packages, Welcomes, commits, retries, and acknowledgements are matched on `(conversation_id, transaction_id, peer)`; stale, substituted, cross-transaction, and legacy v1 frames are rejected. A bounded 512-entry memory-only cache of `(PeerId, SHA-256 digest)` pairs suppresses exact authenticated replays of terminal frames, while KeyPackage and GroupJoin request repeats stay idempotent so a lost response can be retried. The cache stores no frame bodies and is not durable or replay-proof on its own; its eviction window is supplemented by the durable log below for exact authenticated control frames. The post-M13 control log persists only public PeerId bytes, SHA-256 digests of already authenticated signed frames, and a repeatable flag in 4096 bounded AEAD records under `Purpose::Db` with HMAC blind indexes. `Vault::unlock` detects a database older than the profile-bound-AAD anchor and anchor tampering, but a full vault restore including the anchor is not locally detectable and no external anchor exists. The log/anchor do not restore OpenMLS group/ratchet, pending key-package, or channel state, and the anchor is not a backup.
- Group commits are merged locally and remain pending until required acknowledgements are verified. A disconnected required member can leave an operation pending; the UI reports that honestly and does not time out, roll back, or claim completion.
- A removed member stays on the excluded MLS epoch and cannot decrypt future group traffic. Stale-epoch ciphertext from that member is rejected by remaining members. No member can be added without a direct connection and a validated KeyPackage.
- Group text is delivered only after receipts from every expected member. One disconnected recipient holds the operation's ciphertext copy in memory and prevents `Delivered`; the queue does not survive restart or lock.
- Direct connect and all four application protocols, including M13's opaque control protocol, are implemented and tested. `MessageEvent`, `SetupEvent`, `FileEvent`, and `ControlEvent` use redacted `Debug` output that reports lengths but never opaque request/response bytes. Identify and ping remain off by default; when identify is explicitly enabled, protocol/agent strings are bounded and listen addresses are hidden, but the protocol list is still not cross-checked by the application.
- Explicit libp2p pending-socket caps now bound concurrent inbound and outbound handshakes before Noise authentication; authenticated global/per-peer/per-IP limits, duplicate-dial rejection, and sliding-window request/byte budgets remain in place. Expired rate-limiter peer entries are removed, and a peerless transport failure is reported as an event without overwriting cached live connections. These controls do not authenticate the human behind a PeerId, prevent Sybil identities, hide metadata, or replace application-level authorization. The per-IP pre-auth cap applies to raw direct TCP sockets; relay upgrades and distributed floods remain outside that local admission rule.
- File transfer is bound to 64 MiB total, 256 KiB chunks, 256 chunks, and one active transfer per peer in a joined conversation. Active transfers have an inactivity deadline and `abort_file`; `ReleaseApproval::Cancelled` applies only to a verified transfer and blocks release. An already queued worker request cannot be withdrawn through the pinned transport API, so abort ignores late responses instead.
- The file content key is protected by end-to-end Noise and is never persisted. No relay is configured by default. M13 relay support is opt-in; the pinned libp2p relay forwards opaque Noise-protected bytes and does not see the framed offer or content key. File transfer is explicitly refused on observed relayed connections as a conservative metadata/policy choice until a dedicated relay-safe file-key/transport design exists.
- `IntegrityVerified` means the bytes matched the signed SHA-256 manifest only. It is not malware safety, format validation, or a scan result. `ScanStatus` is `NotApplicable` before verification and starts as `Unavailable` afterward.
- The M8 scanner interface is application-supplied and returns exact categories. Only `SecurityConfig::scan` can create a `ScanOutcome`, including its private validated `FileFormat`. The desktop app configures no scanner, so it never displays a clean scan result.
- Structural validation supports TXT (UTF-8 without disallowed control bytes), PNG (signature, chunk lengths, CRC, IHDR, IEND), and GIF (header, color tables, blocks, trailer). A claimed-format mismatch returns `UnsupportedFormat` before a scanner is invoked. These checks are not malware detection, general media parsing, or MIME sniffing.
- Policy release requires a validated format, clean scanner outcome, cross-platform safe base name, non-empty bounded size/chunk count under an unraisable 64 MiB cap, explicit extension allowlist, and explicit per-file `Approved` status. Released bytes are returned only in a zeroizing `ReleasedFile`; the release path writes no plaintext. The desktop app copies them into the encrypted attachment store, and the native save helper used by the OS dialog is the only plaintext disk write: it sanitizes the suggested name, refuses a pre-existing symlink, creates `0600` files on Unix, syncs bytes, and reports only static errors.
- `ReleaseApproval::Cancelled` is terminal for release of a verified transfer. It does not delete verified quarantine ciphertext and does not affect an active transfer; active transfers use the deadline or `abort_file` instead. Quarantine deletion defaults to `Retain`; under `Explicit` it requires a verified transfer that was released or cancelled. Stored-attachment deletion is a separate explicit action and now checks the blob path for symlinks before removing its database record. Filesystem deletion is not secure erasure on SSD/CoW storage.
- Attachments use a random per-file key wrapped under `storage/attachments`, an HMAC blind index, encrypted metadata, and a SHA-256 recheck on read. Read and explicit delete both reject symlinked blob paths, and delete checks before removing the record. Raw DB/WAL/SHM/blob sentinel scans cover names, payloads, and format labels. Windows ACL hardening remains a target.
- Vault encryption at rest is tested on Unix by scanning `profile.db`, `profile.db-wal`, and `profile.db-shm` for plaintext sentinels and raw private-key bytes. Restricted directory permissions, final-path symlink refusal, and quarantine ancestor/parent-component checks are enforced on Unix only.
- Argon2id runs on a dedicated `std::thread` per vault operation. The network worker owns its own Tokio current-thread runtime; there is not yet one shared application Tokio runtime with a blocking pool.
- Password-guessing resistance depends on the user's passphrase. Forgetting the password means permanent data loss; there is no escrow or recovery promise.
- The vault directory is under the OS local-data directory (`~/.local/share/p2p-messenger` on Linux) or a local fallback; the UI shows the real path.
- Default bootstrap, relay, discovery, identify, ping, AutoNAT, and DCUtR settings are empty/off everywhere; no developer-operated service is configured.
- M13 discovery events are advisory candidates only: no auto-dial, contact save, fingerprint verification, or delivery claim follows from mDNS/Kademlia. Relay events are transport observations only; relay operators can see IPs, timing, and sizes and can deny service. AutoNAT/DCUtR results are best-effort, not universal NAT reachability.
- M13 control frames are opaque transport observations. The controller drains them but derives no presence, capability, delivery, trust, or safety state. `NetworkPrivacyStatus` separates configured flags/counts from counters and strings changed only by real libp2p events; cumulative reservation, circuit, and identify values are labelled as observed since startup, while relayed connections are the latest live transport observation.
- Identify, when explicitly enabled, hides listen addresses and bounds peer-provided strings, but it still reveals a protocol/agent description and does not authenticate the human behind the PeerId. There is no Tor/I2P/mixnet, anonymity, or metadata confidentiality claim.
- GUI shows real observed connection state and explicit "Not configured"/"Not implemented" rather than fake connected, verified, delivered, or clean states.
- Release packages are unsigned by default and macOS DMGs are not notarized. `SHA256SUMS` verifies artifact integrity against the release channel, not developer identity or malware safety. Signing is operator-controlled and no signing secret is stored in the repository. There is no auto-updater, telemetry, or phone-home endpoint.
- The native window was built successfully but not visually inspected on this headless host (no display server). CI and a desktop host should do the visual check.

## Important architectural decisions
- ADR-0001: no mandatory centralized infrastructure; direct connect works with zero bootstrap peers.
- ADR-0002: every conversation, including 1:1, is an MLS group.
- ADR-0003: password wraps a random master key; domain-separated subkeys; password change never bulk re-encrypts data.
- ADR-0004: initial identities are device-specific, portable only via explicit encrypted export/import.
- ADR-0005: superseded.
- ADR-0006: pure Rust GUI with egui/eframe; no npm/TypeScript/webview.
- ADR-0007: separate signed file protocol, fresh direct-only content key, bounded AEAD chunks, signed manifest commitment, ciphertext-only quarantine, narrow format validation, explicit approval before release, encrypted attachment storage, user-chosen native OS save, explicit deletion policies, and no clean/safe status without an independent scanner.
- ADR-0008: extend the existing signed `MLS1` protocol with bounded group-control frames; creator-as-admin policy; locally merged commits with pending acknowledgement state; Welcome-based join; all-member delivery receipts; no fourth wire protocol.
- ADR-0009: channels are bounded `CHN1` application bodies inside one MLS group; `channel_id` is in authenticated MLS plaintext; creator-as-admin channel policy with local membership enforcement; legacy receipts; no new wire protocol, new MLS group, or cryptographic channel ACL.
- ADR-0010: source-first cross-platform release packaging with native runners, portable archives plus platform installers, checked checksums, optional operator-controlled signing, no auto-updater/telemetry, and no mandatory centralized infrastructure.
- ADR-0011: M12 hardening chooses bounded, testable local safety checks and honest non-claims over unverifiable Windows ACL/secure-erasure promises.
- ADR-0012: M13 optional discovery, relay, NAT, identify, and control capabilities remain off by default; observations are advisory and are never promoted to trust, contact verification, delivery, or anonymity claims.
- ADR-0013: post-M13 schema v4 durable control-log digests with a chained, AEAD-protected, profile-bound anchor provide partial rollback detection only; they do not restore MLS state and cannot detect a full vault-plus-anchor restore.
- ADR-0014: accepted phased plan for a vault-backed encrypted OpenMLS `StorageProvider`. Phases 1–2 implement schema-v5 opaque MLS-value storage with versioned `Purpose::Db` AAD, blind indexes, per-group chains, unlock verification, and a v2 anchor with authoritative MLS watermarks. Phase 3 implements the staged provider adapter with atomic flush, tombstones, and a tested `MlsGroup::load` round trip; Phase 4 (controller/GUI restore and policy reapplication) remains design only. No numbered milestone, wire format, or mandatory infrastructure is introduced; Phase 3 reuses existing workspace OpenMLS/serde dependencies without new locked packages.
- `libp2p` is pinned to `=0.57.1` with `libp2p-request-response =0.30.0`. The earlier 0.57 conflict is resolved by using egui/eframe 0.35, whose `js-sys ^0.3.77` requirement is compatible with `libp2p-swarm 0.48.0`'s exact `wasm-bindgen-futures =0.4.58`. The codec was migrated to the RPITIT `Codec` trait without changing bounded framing.
- OpenMLS `0.10.0-rc.1` with provider/traits `0.7.0-rc.1` is pinned because it carries crypto-bigint 0.7.11 and clears RUSTSEC-2026-0387; this is a Phase 0 remediation choice, not a production-readiness claim. `openmls_sqlite_storage` was validated but not enabled because SQLite storage of MLS secrets would violate encrypted-at-rest requirements without another encryption layer.
- MLS setup/group control and file transfer are separate versioned protocols, not message kinds. Setup and group-control frames share the same signed `MLS1` protocol and codec; the transport never interprets their bytes, and `p2p-chat` verifies signatures and authenticated peers before MLS or file state changes.
- `rfd 0.18.0` was validated (MIT, MSRV 1.92, current docs.rs/repository) and is an optional native-only dependency; cancelled save dialogs write nothing.
